# 参考：客户 AI 流程改造的「可判定性归因」骨架

一次真实交付（设计中心 AI 落地）沉淀的论证结构。做**任何"客户流程该不该上 Agent"的一页纸**时可直接复用。
适用面很宽：设计、法务、市场、招聘复核、内容生产——凡"有标准化环节 + 有偏好环节"的流程都吃这套。

## 核心判据（全图只回答这一个问题）

> 这个产出，能被「是 / 否」判定吗？

- **能** → 有对错、可校验、可重跑、重做成本≈0 → **Agent 主导**
- **不能** → 没有唯一答案，只能被比较和选择 → **人主导**

一句话版："按可逆性切，不按环节切。" 做错了重做很便宜的给 Agent，做错了要返工几天或赔钱的给人。

## 为什么"每个环节加一个子 Agent + 主 Agent 汇总"是错解

- 每多一个子 Agent，主 Agent 就多一层丢包；n 个子 Agent 通信成本 O(n²)。
- 主 Agent 最后拿到的是 20 份各自局部最优的摘要，拼起来必然失真 —— 这是"各部门信息对不齐"的 AI 版本。
- 结果：表面加了 AI，业务流一点没变，最后还是靠人。
- 正解：**少量 Agent + 强共享上下文**（单一事实源），上下文在协作平台上被共享，而不是在 Agent 之间传话。

## 反例对照：为什么招聘能自动、设计不能

招聘像**考试**：产出可判定（简历符不符合 JD、面试过没过、人到没到岗），错了立刻暴露，所以主 Agent 能推着走，人只当物理世界的一个环节。
设计像**选美**：产出是品味判断，没有标准答案，"不够高级"无法用规则验证，所以照搬招聘模型必然打架。

## 四个环节的归因映射（示例，比例按客户实际调）

| 环节 | 主导 | 可判定占比 | Agent 干什么 |
|---|---|---|---|
| 产品定义 / 竞品调研 | Agent（人给约束） | ~85% | 竞品参数带出处、卖点拆解、定义写成带版本号的基线 |
| 概念发散 / CMF 变体 | Agent（人给种子） | ~70% | 跨界参考、批量 20 个方向、家族语言一致性检查 |
| 偏好审计 / 方案决策 | **人** | ~20% | 20 选 3 并说明为什么否 17 个、对基线签字 |
| 建模渲染 / 提案评审 | Agent 执行 + 人工兜底 | ~60% | 参数化管线、材料齐全度与版本一致性校验 |

## 回跳（改需求）不是流程失败

设计本来就是发散-收敛的循环，跳回第一环节是本质，不是 bug。所以：

- **不要用主 Agent 去协调**（它只会变成丢包点）——给它三件**机械可判定**的事：守版本化基线 / 算变更影响面 / 卡住未评审的闸门。
- 老板要改时不劝，只报数：**"影响 3 个已定稿环节、2 份已发提案、约 6 人日"**，然后给 A/B/C 三档成本的走法让人选。
- 最狠的一招：把「改实现」和「改标准」分开。标准是他自己签的，改标准等于推翻自己——心理成本远高于返工，而且正当（你不是在拦他，是在提醒"这是你自己定的"）。

## 偏好记忆：可归因的否 vs 不可归因的否

人的每一句"不行"要过分拣机：

- **可归因的否**（圆角半径、公差、成本上限、材质合规、卖点缺失、家族语言冲突）→ 量化 → 写进**规则库**，硬约束，Agent 下次自动过滤，不再问第二遍。
- **不可归因的否**（不够高级、气质不对、看着廉价、太像竞品）→ 只进**参考层**，软记忆，影响候选排序，**绝不写成硬规则**。

差别一句话：**硬约束越攒越准，软记忆越攒越像你。两者必须分开存、分开用。**

## 风险：只喂"否"会养出另一个老板

只学否定 → Agent 越来越像老板 → 候选越来越安全 → 设计只剩安全牌 → 企业失去差异化来源。

三条解药：
1. 每轮强制留 10–20% 反直觉方案做对照组，不进规则库筛选，只看人的真实反应。
2. 让 Agent 定期反问："这几次否掉的，有三个共性，是不是你其实不想要 X？" —— 帮人把自己的品味结构化（设计团队最缺的不是产能，是这个）。
3. 发散阶段不吃约束，收敛阶段才用规则；避免一开始就被历史偏好框死。

## 老板频繁发散的三种动机（决定该不该"放大影响"）

| 类型 | 动机 | 对策 |
|---|---|---|
| 信息不对称 | 不知道下游已经做完 | ✅ 报数有效：量化影响面 |
| 标准没锁死 | 看到东西才想起"我要的不是这个" | 前期把验收标准写成人话签字；后期区分改实现 vs 改标准 |
| 权力表达 / 刚看了竞品很兴奋 | 行使控制权或情绪 | ❌ 报数反效果；给沙盒分支（随便改、不碰定稿、采纳才合并） |

**"放大影响"要改成"量化 + 分档 + 归责清晰"**：给数字不给形容词；给 A/B/C 三档而不是问"你确定要改吗"；不替他判断值不值。Agent 一旦开始"劝"，就从工具变成说客，一次被识破后面所有提醒都失效。

## 落点

企业真正的护城河 = **可归因的标准**（可复制、可交给 Agent）+ **不可替代的偏好**（只在人身上、只能被参照）。
AI Native 不是把流程自动化，是把这两样东西**分开存放**。

## 落地策略（别做端到端全流程 Agent）

先把**一个环节**做成版本化基线（通常是产品定义），"改需求就全乱"这个最大痛点立刻有解，而且它天然长成后面所有环节的地基。反过来先做生成/发散，做得再花哨，老板一改需求还是全废。
