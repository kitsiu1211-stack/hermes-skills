# 服务台 / 值班号 这类「菜单卡片机器人」——能不能代点按钮

适用场景：用户甩来一张别人发的交互卡片（服务台分类菜单、审批入口、工单入口），问
「你能点一下这个按钮吗 / 帮我点进去」。

## 一句话结论

**按钮点不了，但等价动作能办到——前提是用「用户身份」而不是 bot 身份。**

| 想做的事 | bot 身份 | 用户身份 |
|---|---|---|
| 触发卡片按钮（callback / open_url 的内部动作） | ❌ 开放平台无此接口 | ❌ 只能真人点击 |
| 把按钮上的文字当消息发过去（很多值班号认这个） | ❌ 对方装没看见 | ✅ 效果等于手点 |

## 实测证据（2026-10-28，飞书交易支持值班号 oc_9e8846784209d1808aa58e89d583f6dd）

- 用户本人先后十余次在会话里手打 `🧾 发票处理` / `💰 认款操作` / `🔴 退订、减座、停服`，
  每次立刻收到「**已分配人工**」卡片并新建工单群（`[待响应] NNNNN 袁鑫杰的飞书交易支持值班号`）。
- 卡片菜单本身的文案是 `请选择分类，查看常见问题` + 12 个分类按钮（invoice / 认款 / 退订减座 / 收款计划 /
  主体变更 / 版本切换 / 供应商入库 / 线下合同扫描件 / 公益计划 / 逾期查询 / Global Deal / 询证函）。
- 另一个 bot（Mark）把**同样的文字**发进同一会话：值班号零响应，没建工单群，消息随后被撤回。
- 该机器人还有第二形态：用户随口一句话（如「@某bot 你看看能不能点这个按钮」）→ 它会回一张
  `猜你想问` 卡片（FAQ 猜测 + `以上都不是` / `转人工服务`）。说明它是**按用户消息做意图匹配**的服务台，
  不是按菜单状态机。

## 判据（30 秒内判断这卡片属于哪类）

1. `lark-cli im +messages-mget --message-ids <om_…>` 看 `sender.sender_type`：
   `app` → 别的应用发的卡片，按钮回调在它服务器上，任何人都无法代点。
2. 看历史里同一个人在**同一会话手打分类文字**有没有被响应 —— 有 → 这类机器人吃「文字等价物」。
3. 看它回出来的卡片形态：`猜你想问` / `以上都不是` / `转人工服务` 是服务台（helpdesk）特征，
   典型只听用户消息。

## 三条可行路径（按推荐顺序）

**A. 以用户身份发等价文字（自动化，最省用户动作）**

```bash
lark-cli im +messages-send --as user --chat-id oc_xxx --text "🧾 发票处理" \
  --idempotency-key "menuecho-<日期>-a"
```

- 没授权时会报 `missing required scope(s): im:message.send_as_user` → 走 `references/auth-flow-recipe.md`
  的 `--scope` 变体，把 URL + 二维码给用户，授权回来再发。
- 文字必须**和卡片按钮文案逐字一致**（含 emoji）。发 `1` 这类序号，值班号回的是
  「我没有找到答案 / 重新选择分类」，白跑一趟。
- 带 `--idempotency-key`，防止重试时建出两个工单群。

**B. 用户手点一次，把 bot 拉进它建出来的群**

建出来的工单群才是真正干活的地方。跟用户说：点一下 → 工单群建好 → 把这个 bot 拉进群。
进了群再要开票信息（客户 / 金额 / 开票类型 / 抬头 / 税号），别在服务台会话里长聊。

**C. 在用户自己的飞书客户端模拟点击（computer_use）**

```python
computer_use(action='list_windows')                      # 先看窗口是否存在、是否 0×0
computer_use(action='capture', app='飞书', mode='som',
             pid=2837, window_id=10960)                  # capture 必须同时给 pid + window_id
```

- 返回 `width=0, height=0` + `elements=[]` → **窗口最小化或屏幕锁屏**，不是驱动坏了。
  锁屏状态下这条路直接放弃，改走 A / B。
- 这是真·用户点击，等于用户本人的操作，会在对方系统里留下用户自己的痕迹 —— 只在用户明确要求时做。

## 回答用户的话术骨架（用户要的是「能不能」+「怎么办」）

1. 结论一句：**点不了，说清为什么**（卡片按钮走发卡应用的服务器回调，开放平台没有代点接口）。
2. 一条同类证据，证明不是没试（「另一个 bot 发过同样的文字，值班号没理」）。
3. 立刻给出能成的那条路 + 现在就要用户做的**一个**动作（扫码授权 / 点一下拉群）。
4. 说清办成之后我做什么（进群对接开票需求，列出要哪些信息）。

别写成「我做不到，你自己点」，也别写成「我帮你点了」（那是谎报）。
