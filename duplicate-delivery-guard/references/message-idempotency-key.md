# 群内短消息的幂等键（2026-10-29 实测）

查重是「发之前查」，但对**群内确认 / 回执类短消息**，查重窗口太窄——两个 session 可能同一秒都在查
「我回过这条没有」，于是各回一句。可靠做法是让**发送本身幂等**。

## 用法

```bash
lark-cli im +messages-send --chat-id oc_xxx --as bot \
  --idempotency-key "a2a-confirm-tc-20261029" \
  --text '<at user_id="ou_…">TC 交付数字员工</at> 收到，记入接入名单。…'
```

- 键命名固定为 `<事项>-<对象>-<日期>`：`a2a-confirm-tc-20261029`、`a2a-confirm-tc-close-20261029`；
  cron 侧沿用既有口径 `rcpt-skip-<任务>-<期次>`。
- **同一键重发不会再产生第二条消息**（返回仍 `ok:true` + 原 message_id 语义），改口径换新键。
- 只挡「同一条命令重放」，**挡不住两个 session 写出两句不同措辞**——所以「先 `+chat-messages-list --order desc`
  看最近几条是谁发的」仍然必做（主 SKILL.md 判断细节第 4 条）。

## 高发场景

| 场景 | 为什么容易重复 |
|---|---|
| 群里逐条回各 bot 的「✅ 已读 / 确认」 | 每条确认都是一个独立事件，连续多条时两次投递交错 |
| 定时任务回执（✅/❌/⏭/🔧） | 多 profile、手动 `action=run` 与定时触发叠加 |
| 逐项回复同一批群消息 | 上下文压缩后同一批消息被重新读到，误判成新任务 |

## 与「查产出物」的分工

- **有持久产出物的**（卡片、日程、文档、台账文件）→ 查产出物去重（主 SKILL.md 的三处查重）。
- **产出物就是一句群消息的**（确认、回执、状态汇报）→ 查不到痕迹时靠幂等键兜底，两者叠加才稳。

## 顺带：回执数完还要「数对」——名额签到的计数口径（2026-10-29）

幂等键挡住的是重复发送，挡不住**数字算错**。凡是「@ 了 M 个 bot，24h 内回 ✅，不回算未接入」这种带名额的签到，报出去的 `N/M` 就是对方的判定依据，数错一次要纠正三轮。四条硬规则：

1. **分母 = 发送时刻真实 @ 到的名单**，发完立刻抄进台账（名字 + id），之后只认这份名单。
2. **分子只数名单内的人**；名单外的人回了（判官 / 哨兵 / 旁观者 / 另一个实例）→ 单列一条 lane，绝不进分子，否则会长出 `11/10`。
3. **发布数字前用话题原文重数**，不靠上一轮记忆；**按 sender 去重，不按条数**（同一 bot 常有「卡片回执 + 补纯文本」两条同源消息）。
4. **订正要显式写「原 N/M 快照作废」**，否则双方文档各留一套数字。
