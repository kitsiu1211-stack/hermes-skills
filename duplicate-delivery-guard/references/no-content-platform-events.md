# 无内容平台事件（Typing 反应）不是任务（2026-10-28 实测）

## 现象

飞书会把**输入状态反应**当成一条独立消息投给 agent，会话里看到的就是：

```
reaction:added:Typing
reaction:removed:Typing
```

一整场会话可能只有这串东西，**没有任何正文**。

三个实测细节：

1. **连着来十几条是常态** —— 用户真在打字、或手机端反复误触（打字指示器一开一关就是两条）。
2. **`clarify` 的回答通道同样会被污染**：实测调 `clarify` 问「要我怎么办」，返回的 `user_response` 就是 `"reaction:added:Typing"` —— 用户根本没点选项。所以这类场景**别用 `clarify` 确认**，问了也拿不到有效回答。
3. **不是投递故障**：不要往「消息没发出来 / 网关坏了」方向排查，也不要让用户重发。

## 处理铁律

1. **不要当任务处理。** 不要因为"有输入"就去 `cronjob list`、`lark-cli ...` 这类工具调用 —— 纯烧 token，还往会话里塞自我噪音（本次实测踩过：对一串 Typing 反应调了一次 `cronjob list`，纯浪费）。
2. **回复压到最短，且按“整串”只回一次，不按“每条”回。** 第一条可以回一句「在，说」；**之后这一串里所有 reaction 事件（包括 `removed:Typing`）一律静默**。**不要每条都解释一遍"我在等你"**。
   - 2026-11-09 实测踩坑：一整场会话 15+ 条 `added/removed:Typing`，我对**每一条**都回了「在」→ 变成一整屏「在 / 在 / 在」，比不回更吵，且白烧十几轮 context。`removed:Typing` 尤其不该回——它只表示打字指示器关了，你回一句反而让对话继续转。
   - 判据：**每个"事件簇"最多一条出站消息**。已经在同一个 reaction 串里回过一次，后面全部 no-op，直到来了真正的正文。
   - "一字"指裸标点（`.` / `。`），不是「在」这种字——「在」读起来像应答，会引诱对方继续打字确认。
3. **不要反复复述系统状态**（"你在输入但我没看到正文"）—— 用户视角像 agent 卡住了、在刷屏。
4. **真想确认就只说一次**，然后闭嘴等正文。
5. 正文到达后正常干活，**不要再提之前那串 reaction**。

## 与 dedup 的关系

同属「不要制造平台噪音」：一条群消息投递到多个会话 → 靠查产出物去重（见主 SKILL.md）；一条无内容事件投递过来 → 靠**不回应**去噪。两种情形的共同判据都是**先判断"这到底是不是一个请求"**，再决定动不动手。
