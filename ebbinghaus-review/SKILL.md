# 每日认知对话（原艾宾浩斯复习）

## 设计哲学

**旧版问题：** 「还记得XX吗？」→ 测验记忆，不激发思考。

**新版目标：** 制造认知摩擦，让用户**想**回应。记忆巩固是副产品，思维激活是主产品。

核心公式：
```
每日对话 = 复习（记忆锚点） + 碰撞（认知摩擦） + 纵深（历史/产业线） + 落地（工作映射） + 等你（对话入口）
```

### Obsidian 集成模型：双落点闭环

这个 skill 不是「读 Obsidian → 推卡片」的单向管道，而是一个**双向循环**：

```
┌──────────────────────────────────────────────────┐
│                   Obsidian                        │
│  concepts/ 下 25 个概念文件                        │
│  ┌──────────────────────────────────────┐         │
│  │ Compiled Truth / 关键要点 / 关联主题   │ ← 读取  │
│  │ Timeline                             │         │
│  │ 📌 每日对话（2026-06-23）             │ ← 写入  │
│  │   碰撞 / 纵深 / 落地                   │         │
│  └──────────────────────────────────────┘         │
└──────────────┬──────────────────▲─────────────────┘
               │ 读取             │ 写入新洞察
               ▼                  │
┌──────────────────────────────────────────────────┐
│              每日认知对话                          │
│  ① 选概念（艾宾浩斯算法）                          │
│  ② 搜索最近分享/话题（session_search）             │
│  ③ 生成五层卡片                                    │
│  ④ 推飞书 → 用户看到、回应                          │
│  ⑤ 对话产生新洞察 → 写回 Obsidian                  │
└──────────────────────────────────────────────────┘
```

**两个落点：**
- **📱 飞书卡片** = 每日唤醒层。轻量、对话感、低门槛参与。
- **📁 Obsidian 概念文件** = 长期知识沉淀。每次对话的碰撞/纵深/落地精华追加到对应概念末尾 `📌 每日对话` 区块，时间长了自然形成你的思考脉络。

**为什么要有两个落点？**
- 飞书卡片是即时触达——你不打开 Obsidian 也能被激活。
- Obsidian 是持久化——三个月后回头看一个概念，下面挂着多次对话的痕迹，能看到自己思考的演进。

## ⚠️ 前置校验：Obsidian vault 路径一致性（2026-07-30 新增）

**关键问题：** 两次 cron 执行可能使用不同的 Obsidian vault 路径，导致今日读取的复习历史与昨日写入的不一致。昨天（7/29）的 cron 写入到 `My Great Vault/concepts/`，但今天（7/30）的 cron 从 `Obsidian Vault/concepts/` 读取——于是 7/29 的复习记录「消失」了，导致概念 主题30 在今日搜索中显示 N=1（仅有 7/23 记录），而非正确的 N=2。

**根因：** `~/.hermes/.env` 中的 `OBSIDIAN_VAULT_PATH` 可能指向一个 vault，但用户直接在 `~/Documents/Obsidian Vault/` 下操作。

**每次执行前必须做：**
1. 调用 `search_files(target="files", pattern="*.md", path="~/Documents/Obsidian Vault/concepts")` 确认 concepts 目录是否存在
2. 如果不存在，检查 `OBSIDIAN_VAULT_PATH` 环境变量指向的 vault
3. 如果多个 vault 都含 concepts 目录，优先使用 `~/Documents/Obsidian Vault`（用户直接操作的主 vault）
4. **所有文件读写操作中 vault 路径必须保持一致**——不要一个步骤用 vault A 读、另一个步骤用 vault B 写

**验证方法：** 读取概念文件后，检查文件末尾的 `📌 每日对话` 记录数量是否与预期一致。如果数量少于上次执行时写的数量，说明 vault 路径不匹配。

## 执行流程

每次执行（每天早上 9:00），按以下步骤操作：

### Step 1：获取上下文

1. **读取 Obsidian 知识图谱**
   - 使用 obsidian skill 读取 `~/Documents/Obsidian Vault/concepts/` 下所有 markdown 文件
   - 按文件修改时间排序，识别最近 30 天内有更新的概念

2. **搜索最近分享的内容**
   - 使用 `session_search` 搜索最近 7 天内用户分享过的外部链接（微信文章、报告、论文等）
   - 搜索关键词：`mp.weixin.qq.com`、`arxiv.org`、`github.com`、用户发来的 URL
   - **⚠️ session_search 挂了怎么办（2026-09-19 实战）**：`session_search` 可能报 `Session database not available: disk I/O error (state.db may be on NFS/SMB/FUSE/ZFS)`（工具层的 WAL 读写失败），但同一时刻 `sqlite3` CLI **仍然可读**。此时不要放弃挖掘用户近期工作，直接用 terminal 查：
     ```bash
     cd ~/.hermes && sqlite3 -separator ' | ' state.db \
       "select datetime(m.timestamp,'unixepoch','localtime'), s.source, substr(replace(m.content,char(10),' '),1,300) \
        from messages m join sessions s on s.id=m.session_id \
        where m.role='user' and m.timestamp > strftime('%s','now') - 7*86400 \
        and s.source not in ('cron') and m.content not like '%[IMPORTANT%' \
        order by m.timestamp desc limit 40;"
     ```
     近 7 天会话清单：`select id, source, datetime(started_at,'unixepoch','localtime'), message_count from sessions where started_at > strftime('%s','now') - 7*86400 order by started_at desc;`
     过滤 `source not in ('cron')` 和 `content not like '%[IMPORTANT%'` 可去掉 cron 噪音，剩下的就是用户真实发言。
   - 找到 1-3 篇最近的文章/分享，记录其主题
   - **如果返回结果全是 cron 会话（无用户驱动对话）**：说明用户近期未分享文章。这是正常情况，碰撞层改用概念自身材料（关联主题、历史对话中的案例）来构造问题，不编造文章引用。
   - **最佳替代碰撞素材是用户近期的实际工作**：先 `session_search(sort='newest', limit=3)` 浏览近几天会话，提取用户正在做的项目、规划、与人协作的主题。用户自己正在做的事是最有吸引力的碰撞材料——远比抽象关联主题更具体、有共鸣。应当优先用 session_search 挖掘用户最近议题，再回退到概念自身的关联主题。

3. **搜索近期对话主题**
   - 使用 `session_search` 搜索最近 5 天对话中讨论最多的概念或话题
   - 提取 1-2 个热门主题

### Step 2：选择复习概念

基于艾宾浩斯遗忘曲线，从 Obsidian 概念中选择 **1 个**今天该复习的：

- 优先选择：最近修改过、但 3/7/15/30/60 天前上次复习的
- 次选：用户近期讨论过的相关主题
- 避免：今天已经复习过的（检查当天执行记录）

**复习历史追踪方法（关键）：**

不要依赖 session_search 去找历史复习记录——cron 会话可能被清理或不完整。最可靠的方法：

```bash
# 在 Obsidian 概念文件中搜索所有复习记录
search_files(pattern="📌 每日对话（20", target="content",
             path="<vault>/concepts", output_mode="content")
```

这会返回每个概念文件的所有复习日期。然后按以下算法选择：

**核心算法（2026-07-19 修复）：**
1. 统计每个概念的复习次数 N（= `📌 每日对话` 区块数量）
2. 计算每个概念的「上次复习距今」天数 D
3. 根据 N 确定应检查的间隔 I：
   - N=0（首次）→ 不参与间隔匹配，走优先级 3
   - N=1 → I=7 天
   - N=2 → I=15 天
   - N=3 → I=30 天
   - N=4 → I=60 天
   - N≥5 → 退役，走优先级 4
4. 检查 D 是否落在 I ± 容差范围内（I≥15 时容差 ±3，否则 ±2）
5. 命中的概念按优先级排序，取最高优先级的一个

### Step 3：构建五层对话卡片

每一层都有明确的目的和格式要求：

---

#### 第一层：回顾 —— 「你当时写的」

**目的：** 建立记忆锚点，让用户快速回想起这个知识。

**格式：**
```
🧠 回顾 | {概念名}

{30-50 字核心摘要 —— 不是原文照搬，是精炼后的核心主张}

完整笔记 → Obsidian「{概念名}」
```

**原则：**
- 只给核心主张，不长篇引用
- 用你自己的话重述（去 AI 味）
- 语气：像朋友提起旧事

---

#### 第二层：碰撞 —— 「这个判断还成立吗？」

**目的：** 制造认知摩擦。拿用户最近的经历、分享的新文章、或者行业新变化去冲撞旧认知。

**格式：**
```
⚡ 碰撞

{一个挑衅性问题，用最近的信息挑战旧认知}

比如：
- "前两天你分享的那篇亚洲工业周期的文章里说……这跟你之前的{旧概念}是不是矛盾的？"
- "{旧概念}说的是 X，但最近{新事件}，这说明什么？"
- "如果{旧概念}是对的，那{反例/边界}怎么解释？"
```

**原则：**
- 问题是**真的**值得想，不是明知故问
- 用具体的新信息当碰撞材料，不说空话
- 允许用户反驳你——甚至可以故意站一个极端立场等他推翻
- 语气：对话感，不是考官

---

#### 第三层：纵深 —— 「拉一条线」

**目的：** 用历史类比、产业逻辑、跨领域连接，把单点知识变成纵深理解。

**格式：**
```
🔗 纵深

{历史类比或产业逻辑线 —— 1-2 句话，不要展开成文章}
```

**原则：**
- 精选 1 条最有穿透力的线，不要列一堆
- 优先用用户最近分享的文章里的历史/产业背景
- 如果实在没有合适的类比，可以跳过这一层

**⛔ 纵深类比防重复（强制）：**

每次生成纵深时，必须先**从 Obsidian 概念文件中提取历史类比**，确保本次不使用相同的历史事件/产业案例/比喻。

- 类比 A 和类比 B 的关系：只要核心历史事件/产业案例/比喻相同，就算重复——哪怕换个说法、换个人名、换个年份也算重复
- **已被标记为疲劳的类比（永久禁止）**：
  - 「1873 年铁路危机 → AI 基建潮」（用户已明确厌倦）
- **避重复五步法**：
  1. 用 `search_files(pattern="纵深：", target="content", path="<vault>/concepts", file_glob="*.md")` 搜索所有概念文件中的纵深内容
  2. **同时检查当前被复习概念文件内的 `📌 每日对话` 区块**（用 `search_files` 按文件名过滤），提取该概念所有历史纵深类比。不要只依赖全局搜索——全局搜索可能遗漏同概念下的历史类比（格式差异导致 grep 不命中），也可能搜到其他概念的类比而误以为当前概念没使用过。
  3. 提取每次出现的历史类比/案例/比喻，合并去重
  4. 和本次候选类比比对，确认不在已用清单中
  5. 如果找不到合适的新类比 → 跳过纵深。**跳过比硬塞旧类比好**
- **辅助搜索模式**：也可以 `search_files(pattern="🔗", target="content", path="<vault>/concepts", file_glob="*.md")` 如果前面搜索不到纵深内容
- **⚠️ 相近类比避嫌**：即使核心事件不同，也要检查新类比和旧类比是否共享同一「控制权结构」。例如「NASA 深空探测自主权演化（Mariner→Voyager）」和「东印度公司（伦敦→总督）」都讲「中心放权给边缘」，可能被用户视为同一类。判断标准：如果用户说「这不就是换了个名字讲同一个道理吗」→ 也算重复。选类比时优先选**结构完全不同**的。
- **⚠️ 正则转义注意**：`search_files` 使用 ripgrep 正则引擎。Obsidian 加粗标记 `**` 在正则中是通配符，不要直接复制 markdown 标记如 `**纵深：**` 作为搜索模式——应去掉星号用 `纵深：`。同理，emoji 如 `🔗` 可以直接搜索，但不要加上 markdown 包裹标记。

---

#### 第四层：落地 —— 「跟你有什么关系」（⚠️ 只加在有自然关联时）

**目的：** 把抽象认知映射到用户的真实工作场景。**但只在有强关联时才加，不强套。**

**判断标准：** 你能在 30 秒内想出一个自然的连接点。如果需要绕很多弯、或者明显在硬扯——跳过这一层。

**什么时候加：**
- 概念本身和销售/客户管理有直接映射（如「暗知识壁垒」→ 客户信任建立）
- 概念涉及产业/经济趋势，能和客户行业对上（如「工业超级周期」→ 制造业客户回访）
- 概念涉及组织协作，能和内部协调对上

**什么时候不加：**
- 纯技术概念（如「FP16 精度」）硬套到「你怎么说服客户」——跳过
- 联系太勉强，需要长篇解释才能圆回来——跳过
- 用户自己都没把这概念和工作联系起来过——跳过

**格式：**
```
🎯 落地

{只有当关联自然时才加入，不强套}
```

**原则（仅在加入时）：**
- 用用户的词（飞书、客户回访、CRM、增购、存量保护）
- 用用户的场景（说服客户、内部协调、商机跟踪）
- 问「怎么做」，不问「是什么」

---

#### 第五层：等你 —— 「想听听你的」

**目的：** 留一个开放式对话入口，降低回应门槛。

**格式：**
```
💬 想听听你的

{一个低门槛的开放式问题，用户可以随便说一句就参与}

比如：
- "上面哪个点最戳你？回我一句就行"
- "你觉得这个类比靠谱吗？还是我在硬扯？"
- "你最近有没有碰到过跟这个相关的场景？"
```

**原则：**
- 门槛极低，不需要长篇大论
- 可以表达不同意见
- 像朋友聊天收尾

---

### Step 4：发送卡片

使用 `lark-cli im +messages-send` 发送交互式卡片到 **Home 私聊**（固定 chat_id `oc_e2f79ec1614a1efe1ebcd7c679bb45a8`），不落到任何群聊。

**⛔ DNS 解析失败 ≠ 断网（2026-11-07 踩坑）:** 发送报 `dial tcp: lookup open.feishu.cn: no such host` 时，先别以为网络挂了。实测现场：`curl https://www.baidu.com` 返回 200、`dig +short open.feishu.cn` 正常出 IP、`nslookup` 也正常，但 `python3 socket.getaddrinfo` 和 lark-cli 都报 no such host——这是 macOS mDNSResponder 对该域名的负缓存（`dscacheutil -q host -a name open.feishu.cn` 返回空），不是网络故障，也不要用 sudo 刷缓存（cron 无密码权限）。

**解法：给 lark-cli 加 `GODEBUG=netdns=go`**，强制 Go 走纯解析器直读 `/etc/resolv.conf` 的 `nameserver 127.0.0.1`，绕过 mDNSResponder：

```bash
GODEBUG=netdns=go LARKSUITE_CLI_NO_UPDATE_NOTIFIER=1 LARKSUITE_CLI_NO_SKILLS_NOTIFIER=1 \
  lark-cli im +messages-send --as bot --chat-id "$CHAT_ID" \
  --content "$(cat /tmp/ebbinghaus_<date>_card.json)" --msg-type interactive
```

验证通路是否真的通（不发消息）：`curl --resolve open.feishu.cn:443:<dig出的IP> https://open.feishu.cn/` 返回 404 即说明 TLS/网络正常，问题只在域名解析。**GODEBUG 变量建议固定加在所有 lark-cli 调用前缀**，避免偶发解析抖动导致误判失败重发。

**⛔ 双发陷阱（2026-08-19 踩坑）：** 发送命令必须带 `LARKSUITE_CLI_NO_UPDATE_NOTIFIER=1 LARKSUITE_CLI_NO_SKILLS_NOTIFIER=1` 前缀——否则 lark-cli 的版本更新通知会污染 stdout，`tail` 截断后看不到发送结果，容易误判失败而重发，导致用户收到两条相同卡片。发送后如需验证，用 `+chat-messages-list --page-size 3` 查最近消息确认只有一条，**严禁盲发第二次**。

```bash
CHAT_ID="oc_e2f79ec1614a1efe1ebcd7c679bb45a8"
lark-cli im +messages-send --as bot --chat-id "$CHAT_ID" \
  --content "$(cat /tmp/ebbinghaus_<date>_card.json)" \
  --msg-type interactive
```

参考 `feishu-api` skill 的「Message Sending → Interactive Card」章节。

**卡片构建流程：**
1. 用 `write_file` 写完整的卡片 JSON 到 `/tmp/ebbinghaus_<date>_card.json`
2. 用 `lark-cli im +messages-send --content "$(cat ...)" --msg-type interactive` 发送
3. 验证返回的 `ok: true` 和 `message_id`

**卡片格式要求（手机优先）：**

```
Header: 🔮 每日认知对话 | {日期}
Template: indigo

[回顾层内容]
---
[碰撞层内容]
---
[纵深层内容]
---
[落地层内容]
---
[💬 想听听你的]
---
footer: Hermes · 每日认知对话
```

**手机优先规则：**
- Header 标题正常表达不堆大词
- 信息精炼分段，用加粗/分割线/缩进
- 控制在 1 张卡片内
- 每层之间用 `---` 分割

### Step 5：写入 Obsidian

在对话生成后，如果产生了有价值的洞察（碰撞、纵深、落地三层中任一层有实质内容），将内容追加到对应 Obsidian 概念文件的末尾：

```markdown
---

## 📌 每日对话（{日期}）

**碰撞：**{碰撞层核心问题}

**纵深：**{历史/产业线}
 
**落地：**{工作映射}

**⚠️ patch 陷阱：** 使用 `patch` 在 Timeline 表格末尾追加内容时，容易创造多余的空格/竖线导致 Obsidian 表格渲染错乱。安全做法：(1) 用 `write_file` 重建整个文件（需先 `read_file` 拿到未污染的完整内容），或 (2) `patch` 时选表格**上方或下方**的稳定文本锚点（不要选表格行本身），确保 `old_string` 唯一且在表格边界外。

**⚠️ write_file 重建陷阱（2026-07-30，2026-08-05 更新）：** 使用 `write_file` 重建概念文件时，`read_file` 的 Line number 前缀不会被自动剥离——必须手动从 Python 字符串构造内容，或者使用 `execute_code` 中的 `read_file` 工具获取纯内容。
```

## 艾宾浩斯选择逻辑

**⚠️ N 轮次递进算法（2026-07-19 修复——旧版 flat 间隔已废弃。参见 `references/interval-calculation-worked-example.md` 的完整含表示例）：**

旧版 Bug：只检查「距上次复习天数是否命中 3/7/15/30/60 任一间隔」，不跟踪概念在第几轮复习。导致每次复习完 3 天后又被 3 天间隔重新命中 → 无限困在最短间隔。

**正确做法（必须严格遵循）：**

```
1. 读取概念文件的「📌 每日对话」区块，统计已有复习次数 N
2. 根据 N 确定本次应检查的间隔：
   N=0（首次）→ 不检查，所有概念平等竞争
   N=1 → 应检查间隔 = 7 天（不是 3 天！）
   N=2 → 应检查间隔 = 15 天
   N=3 → 应检查间隔 = 30 天
   N=4 → 应检查间隔 = 60 天
   N≥5 → 退役，优先级最低
3. 只检查「距上次复习天数是否落在应检查间隔的 ± 容差范围内」
4. 严禁同时检查多个间隔——只检查 N 对应的那一个间隔
```

**示例：心跳机制（7/19 复盘验证）**
- 已有复习次数 N=4（6/29, 7/13, 7/16, 7/19）
- 本次应检查间隔 = 60 天（N=4）
- 距上次复习（7/19）60 天后 = 9/17，在此之前不会再次命中
- ✅ 不会在 7/22（3天后）再次被选中

**选择优先级：**
1. 恰好命中**对应轮次间隔**的概念（N=1 检查 7 天，N=2 检查 15 天……）
2. 与最近对话/分享主题相关的概念（仍需间隔检查，不跳过）
3. 30天内更新过但从未复习的概念（N=0，首次）
   - **N=0 多候选排障**（当有多个 N=0 候选时）：优先选 (a) 与用户最近1-2天实际工作关联最强的（session_search 搜会话主题），(b) 最近修改时间最接近今天的，(c) 关联主题/碰撞素材最丰富的。不要因「名字更眼熟」随便选——N=0 概念的碰撞威力取决于它能否与用户手上正在做的事发生有效 hook，而非概念本身的热悉度。
4. 兜底：最早未被复习的概念 + 已退役概念中时间最久的

**当无概念命中轮次间隔时的处理（2026-07-30 新增）：**
   - 这是正常情况——所有概念的上次复习时间都不在其 N 对应的 I ± 容差范围内
   - 首先确认是否有概念「昨天刚被推送但未在今天的数据中反映出来」（vault 路径一致性问题可能导致间隔命中概念被「丢失」——参见上方前置校验）
   - 然后走 N=0 候选（优先级 3）
   - 如果 N=0 候选也有多选，用**用户最近实际工作主题**作为主要排序依据（session_search sort='newest' 浏览近 1-2 天会话），而非概念的修改时间
   - 示例（2026-07-30）：主题3-Harness工程（N=0，概念文件上次修改 >30天前）→ 但用户昨天亲手搭了 Harness 三层的代码（校验/突变/依赖图）→ 碰撞威力极强。虽然概念文件「30 天内更新过」条件不满足，但工作上下文关联强度更高，可以作为兜底选择

**多命中时排障（关键）：** 当多个概念同时精确命中同一间隔时，优先选：
- 与用户**最近实际工作**关联最强的（session_search 搜到的项目/问题/对话主题）
- 碰撞材料最丰富的（概念本身的新近对话多、关联主题广）
- 注意：不要因为某个概念「更熟悉」就默认选它——碰撞的威力来自「拿用户最近在做的事去冲撞旧认知」，这个概念和用户最近做的事之间交集的强度才是第一权重

> **实战参考**：`references/interval-calculation-worked-example.md` 包含完整 N 轮次算法的命中筛选过程（含 2026-07-27 实际匹配表、与旧版 flat 间隔的对比、执行技巧）。

**防重复：**
- 同一个概念按递进间隔推进，不会在同一间隔重复
- 如果某个概念被意外重复选中（如手动触发），检查 N 是否匹配轮次，不匹配则跳过
- **与每周综合复盘互斥：** 如果某概念在过去 7 天内已被「每周综合复盘」（每周五 18:00）详细覆盖过，跳过该概念。判断方法：检查该概念文件的 `📌 每日对话` 区块中是否有最近 7 天内的记录——如果有且在周五±1天范围内，说明已被周复盘覆盖

## 常见执行问题

### 用户近期无对话

当用户连续多天未发起飞书对话（只有 cron 任务在跑）时：

- `session_search` 搜索文章/分享关键词只会返回 cron 会话，不含用户实际分享的文章
- **这是正常现象，不是搜索失败**。此时碰撞层不能依赖「用户最近分享的文章」，而应使用概念自身的材料（关联主题、Timeline 中的历史对话）来构造碰撞问题
- **最佳替代碰撞素材是用户近期的实际工作**：用 `session_search(sort='newest', limit=5)` 浏览近几天会话，提取用户正在做的项目、规划、与人协作的主题。用户自己正在做的事是最有吸引力的碰撞材料——远比抽象关联主题或历史对话案例来得具体和有共鸣。应当优先用 session_search 挖掘用户最近议题，再回退到概念自身的关联主题
- 不要因为没有找到用户分享就跳过碰撞层——碰撞层是必须的，换个素材来源即可

#### 实战案例（2026-07-22）：概念即用户自身痛点的碰撞——「教练的手够不够到自己的脖子」

当复习概念的核心变量恰好就是用户**近期自己犯的错/遇到的挫败**时，碰撞层获得「自我指涉」的特殊力量——用户本人的现场失误是最好的碰撞素材，因为它同时具备**即时性、具体性、情感共鸣**：

- **复习概念**：主题28-晋升驱动AI转型（核心公式：拉力×使用门槛降低。使用门槛越低，越多人能上手）
- **用户近期痛点**：AI认知摸底H5搭建过程——消息被Feishu截断、@错botKimi没收到、Kimi搭完无验收。用户自己复盘时承认：「我配好了这些机制，你还出现这个问题。我对你这个整个任务的完成度非常不满意。」
- **碰撞构造**：不是反问「使用门槛降低到多少才够」，而是直接用用户昨天的协作失误去冲撞他自己提出的公式——「你在教别人降低门槛，但你自己被自己搭的工具绊倒了。门槛降低对学员成立，对教练本人也成立吗？教练的日常复杂度天然更高，公式缺了一个变量：公式对谁成立？」

**原则**：如果用户在最近1-2天内有明显的协作失误、重复性崩溃、或对工具链的抱怨，而这些失误恰好与复习概念的核心变量有关（使用门槛/反馈循环/协作规则等），优先用它作为碰撞材料。**用户自己的挫败感是最强的认知摩擦点**——他刚刚经历过，不需要回忆和构建，碰撞直击当下。
**特别价值**：这种碰撞同时具备「自我指涉」的效果——用户不仅在思考概念本身，还在思考自己刚刚的行为与概念的关系。远比「前两天分享的一篇文章」有代入感。

#### 实战案例（2026-07-19）：概念 + 同族新概念交叉碰撞

当被复习概念与用户近期项目直接相关、且用户同期正在推进一个**同族新概念**时，碰撞层可以「踩在同族概念的桥上」制造更大的认知摩擦：

- **复习概念**：主题27-心跳机制价值函数（心跳的噪音/价值比取决于上下文厚度）

- **碰撞构造**：不是直接拷问心跳机制的价值公式，而是把心跳的问题翻译到新概念领域——「心跳在管什么值得推给你，信息联动在管什么值得记住。你给团队智能体装了记忆，给它装了联动机器吗？」——既不重复心跳本身的已知争论，又把两个概念的同时存在转化为一道**用户必须自己解释的问题**

**原则**：当近期有强相关的同族新概念被创建/深入讨论时，优先用它作为碰撞材料。这比用概念自身的历史对话更有时效性，也比空泛的行业类比更有咬合力。

#### 实战案例（2026-07-21）：同日讨论作为碰撞材料

当用户**当天早上**刚深入讨论过的框架，恰好与复习概念形成张力时，它是时间上最近的碰撞材料——比任何历史对话都新：

- **复习概念**：主题19-Context not Control 的三层同构（N=2，上次复习 7/9，15天间隔命中）
- **同日讨论**：用户今早深度参与「Loop 工程 → Graph 工程」讨论（Rahul 五层架构：Prompt→Context→Harness→Loop→Graph），并在讨论中决定落地 Loop 自检（知识捕获 v1.1.0 的 Generator→Evaluator→Semantic Check 管线）
- **碰撞构造**：不是拷问 Context not Control 的基本定义，而是抓住同日讨论中的核心矛盾——「你刚跟你的 Agent 说'不设 Control'，又给知识捕获装了自检（阈值10/15、三维度评分写死），这些规则是 Context 还是 Control？」——直接用用户当天亲手写的配置反问，制造了即时性和特异性。
- **特别价值**：用户当天上午的讨论内容是最鲜活的碰撞材料，比"前两天分享的一篇文章"更有代入感。甚至可以让用户感觉「这个 Agent 真的在跟进我的工作进展」，而不只是读笔记。

**原则**：执行 cron 任务前，先用 `session_search(sort='newest', limit=3)` 检查用户**当天/前一天**是否有实质性对话。如果有，优先提取其中与被复习概念有 tension 的主题作为碰撞材料。这比"最近 7 天内文章"更具时效性和共鸣感。

当复习概念本身**就是用户最近在做的项目**时，碰撞层获得「第一性」素材：

- **复习概念**：主题27-心跳机制价值函数（探针层→推理层两层架构，上下文阈值决定噪音/价值比）

## 用户回应后的对话规则（⚠️ 关键）

每日认知对话不是单向推送——卡片发出后，用户在飞书里的回复才是主菜。以下是回应规则：

### 做：深度对话，连接知识图谱

- 用户分享新观点/新经验时，**先对话，后归档**。第一时间做的是：连接到 Obsidian 中的关联概念、提出挑战性问题、延伸思考——不是先把话记下来。
- 从用户的回复中提取**概念层面的新洞察**，看是否能与 Obsidian 现有概念产生碰撞或延伸。
- 如果用户的观点挑战了某个旧概念，直接指出来：「你说的这个，其实跟你之前 XX 概念是矛盾的/补充的——你怎么看？」

### 不做：机械归档

- **禁止**只回复「记下了」「已保存到 Obsidian」然后就结束——这是归档行为，不是对话行为。
- **禁止**把用户分享的人生哲学、工作方法论仅仅当作「偏好」存到 memory 然后翻篇。这些往往是 Obsidian 概念的活体延伸，值得深入讨论。
- 如果用户说「你好像没有跟我做深入沟通，只是记下来而已」——你已经犯了这个错误。立刻切换到对话模式，连接知识图谱，追问。

### 写入 Obsidian 的时机

- 在**对话结束后**（不是一个来回就写），确认产生了实质性的新洞察再追加到对应概念文件。
- 写入内容格式同 Step 5，追加在概念文件末尾的 `📌 每日对话` 区块。

## 质检：Generator → Evaluator（强制）

本 Skill 产出复习内容推送用户，**必须经过 Evaluator 独立评分后才能交付**。

| 维度 | 阈值 | 检查要点 |
|------|------|---------|
| **概念关联度** | ≥7 | 复习内容是否真正连接了用户的工作场景？还是泛泛回顾？ |
| **时效准确性** | ≥7 | 间隔天数是否准确？是否遗漏了更应复习的旧概念？ |
| **可执行性** | ≥7 | 用户读完能否立刻有收获？有没有具体的新角度而非重复原概念？ |

**执行方式：**
- **有人场景（用户在线对话中）**：用 `delegate_task` 派给子Agent做 Evaluator，等待评分反馈。禁止自评。
- **Cron 场景（无人、一次性推送）**：没有子Agent可用时，Generator 在执行末尾自评三个维度，确认均≥7后再交付。如果任一维度 <7，修正并重评（最多3轮）。自评时记录每维度的评分理由，确保不自欺。

**注意：** 回顾层不应超过50字核心摘要；碰撞层必须有具体、新鲜的信息作为材料（不是抽象提问）；纵深如果选类比，必须做防重复检查；落地层如果不自然就跳过——不跳过的自评低于7也不能交付。
