# 复盘「用户自己的分享」（highlight / lowlight）+ 旁听进程启动自检

本 skill 主文件里的输出变体覆盖了「内部复盘/周会」「培训宣讲」「客户调研」等场景；本页补一类**专门评估用户本人发言**的产出，以及采集阶段的启动自检。

## 一、触发与语气

用户原话形如：「你听了我整场的分享吧，**我这场的 highlight 和 lowlight 是什么**？」

- 要的是**诚实评估**，不是表扬。**该扣分就扣分**，不堆形容词、不写「讲得很好」。
- 固定输出结构：`✨ Highlight` → `⚠️ Lowlight` → `一句话总结 + 一个最高优先改进项`。**只给一个最高优先改进项**，不要十条并列建议——并列建议等于没建议。
- 用户接受「没做到 + 原因 + 补救选项」，不接受把推断包装成事实。

## 二、定位「他自己那一段」（零 token）

JSONL 去重 + 按时间排序，然后打**说话人句数排行 + 每人时间区间**：

```
袁鑫杰  156 句  09:02–09:48      ← 开场主讲 + 结尾提问
陶良乐  100 句  09:22–09:31
钟润梓   95 句  09:31–09:43
刘钊     52 句  09:18–09:49      ← 全程提问/点评
```

一眼得到三件事：**他讲哪一段**、**他在全场占多重**（实测 33%）、**谁在他之后点评**（刘钊的 52 句里含对他的追问）。用 `scripts/transcript_paragraphs.py` 的体检报告即可，或手写时按上面的去重+排序口径。

## 三、必须连读「紧随其后的他人反应」

🚨 亮点和暗点**多半不在他自己嘴里，而在别人对那一段的反应里**。`chat`（弹幕）事件要单独按时间轴读一遍，别只看 transcript。

实测案例：他讲完后，总监在弹幕里发了 3 条**提问**（客户 IT 基础设施整理情况 / 豆包工作坊提及 / CSM·售前参与），他当场回「OK，这个是超哥帮我的一个**总结**，谢谢」→ 总监立刻纠正「不是给你的总结，是提问」。这个 8 秒的尬点**才是全场最真实的 lowlight**，只读 transcript 完全看不出来。

同理，主持人/总监在其后的点评里给出的通用要求（例：「讲东西要故事线，不要上来讲框架和功能」）如果正对着他的讲法，就是给他的暗点，要在 Lowlight 里点出来。

## 四、Highlight 的写法：按「可被抄走的资产」

每条都要能落到「**别的同事拿去就能用**」，不要写成「他讲得好」：

- **战法可复制**：把单 SKU 报价改写成整体价值对比、把客户的情绪顾虑（「买了用不完会浪费」）改写成可算的数据题
- **把「AI 难用」翻译成「AI 该这么用」的具体动作**（例：连接器+Skill 放第一段 → @ 单聊/服务群补原始上下文 → 最后只补目的与服务对象），这是全场最方法论级的一段，含金量高于任何单点案例
- **姿态得当**：主动声明能力边界（「不是替代 DM/法务，只做初步沟通」）、承认自己工作里没覆盖到的部分
- **选题踩中会议主轴**：他的案例正好串起本场主题的前两块

## 五、Lowlight 的写法：按四层拆，每层后跟一句「怎么改」

| 层 | 典型形态 | 改法 |
|---|---|---|
| 结构 | 最值钱的方法论被压在**超时后**的末尾（主持人已经在催），本可以当开场钩子 | 把方法论段提到开头做钩子，案例放后面，结尾留 2 分钟做收口 |
| 数据 | 只给了自己的测算（如「99 万 ÷ 365 = 日均 5.48 万点」），**没给横向锚点**（同行业/同规模客户普遍日均多少） | 补一句同类客户的实际区间，让案例具备可对比性 |
| 闭环 | 只讲打法，**没讲战果**（最终切了多少席位 / 续约金额 / 有没有用满） | 每个 case 结尾补战果数字 |
| 边界 | 只在一个 case 里声明了适用边界，另两个没声明 | 每个 case 收尾统一加「适用前提 X / 不适用 Y」 |

补充一条通用暗点：**会中把「提问」误读成「表扬」**（见第三节）——这类误读扣的是印象分，归到结构层里写。

## 附：启动旁听进程的正确姿势（交互式会话）

- 🚨 **不要用 `nohup` / `disown` / `setsid` 起 `poll.sh` 这类长跑脚本**——Hermes 的 terminal 会直接拒绝 shell 级后台包装，提示改用 background 参数。正确写法：
  ```
  terminal(command='bash .../poll.sh <long_meeting_id> "<标题>" bot',
           background=True, notify_on_complete=True)
  ```
  （第三个参数 `bot` = 从一开始就用 `--as bot` 轮询，适合用户不在会、只让 Bot 挂机的场次）
- 🚨 **stdout 绝不能管到 `| head -N` / `| tail -N`（2026-10-16 踩到并当场改掉）**：`head` 读满 N 行就退出并关闭管道，长跑脚本下一次 write 即吃 **SIGPIPE 被杀**。表面上只是「少几行日志」，实际是旁听在会议进行到第 30 行输出时静默死亡，而你以为它还在采。**唯一正确形式是把 stdout 重定向到固定路径的日志文件**（这样工具会话只在脚本真正退出时才给 notify；落盘日志也让会中排查和事后复盘都不必回翻会话输出）：
  ```bash
  # ✅ 正确
  terminal(command='cd ~ && bash ~/.hermes/skills/feishu/feishu-meeting-listen/scripts/poll.sh <long_meeting_id> "飞书信息管控" bot > /tmp/poll_<9位号>.log 2>&1',
           background=True, notify_on_complete=True)
  # ❌ bash .../poll.sh <id> "标题" bot | head -30    → head 退出后脚本被 SIGPIPE 杀掉
  ```
- **起来之后必须另起一次调用做就绪自检（三连，缺一不可）**，进程存活 ≠ 有字幕：
  ```bash
  tail -20 /tmp/poll_<9位号>.log        # ① 应看到「=== 以 Bot 身份启动轮询」「=== 会议雷达已启动」
  wc -l ~/meeting_logs/<meeting_id>.jsonl; tail -2 ~/meeting_logs/<meeting_id>.jsonl   # ② 有行数 + 两句真实字幕
  ps aux | grep -E "poll\.sh <id>|meeting_radar" | grep -v grep                        # ③ poll 与 radar 两个进程都在
  ```
  三连全绿，才可以对用户说「已入会并开始旁听」。拿不到字幕就如实说，别让它静默空跑。
- 只想要「Bot 在场但不说话」时：join 之后**不要**启动语音管线，没有管线就没有 TTS，天然静音。
