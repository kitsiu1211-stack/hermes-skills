# 说话人归因失真的两种形态（长字幕必查）

`vc +meeting-events` 的字幕 `speaker` 字段**不是可靠的人名**。读长转写前先跑 `Counter(speaker)`，命中下面任一形态就按对应做法处理，**绝不要把推断当事实写进纪要**。

## 形态 A：会议室设备名（实测 537/1154 句 = 47%）

speaker 是形如「Shenzhen-Jinghu Plaza(深圳景湖大厦)-F15-03🎦[应急会议室](13)」「康泰创新广场-12F-曼谷 Bangkok(10)」的设备名——会议室那台机器入了会，真人名字混在正文里（谁在投屏、谁自我介绍、谁被点名）。

判断信号：speaker 字符串带楼层/房间/城市编号，或结尾是 `(N)` 数字。

## 形态 B：整场 100% 归到用户本人名下（2026-10-15 客户回访会实测）

730 句字幕**只有一个非 Bot speaker**（就是用户自己），没有任何第二个名字——用户与客户共用一路音源（一台设备收音 / 一个账号入会）。

- 🚨 **最容易犯的错**：把**客户的话当成用户说的**写进纪要——客户抛出的产品诉求会被记成「你提的问题」，交付物一出手就错。
- 做法：① 按内容口吻切分角色（提问 / 追问 / 举自家系统现状 / 吐槽更新＝客户方；给口径 / 讲案例 / 讲方法论 / 承诺回头查＝我方）② 卡片 note 与口头汇报里显式写「本场字幕说话人全部归属到你名下，客户与你的话按内容推断」③ 用户要把这段转给产品/同事当证据时，提醒他**抽几句自核**再发。
- 判断信号：`Counter(speaker)` 只有 1 个非 Bot 名字，而句子数上百（正常多人会至少有 2~5 个名字）。

## 通用收尾

无论 A 还是 B，产出物里都要有一句**归因说明**（`long-transcript-digest` 第三步「⚠️ 这次没做到的 / 归因说明」那块），写明：哪几段无法归因到个人、按什么线索推断的、可能偏在哪。用户接受「没做到 + 原因 + 补救」，不接受把推断包装成事实。
