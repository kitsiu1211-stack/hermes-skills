# 会中主动预警 & 会后冲突归因（2026-10-14 落地记录）

配套：`scripts/transcript_signal_scan.py`（零 token 只读扫描器）；规则集与私聊推送的完整实现见用户自有 skill `feishu-meeting-listen/scripts/meeting_radar.py`。

---

## 一、为什么要分三层

用户原话：「有什么办法能让你**主动**去挖掘会议中的冲突、异常项，或者某个人背后的需求，把这个变成一种主动式的分析？怎么设置，才能让你发现异常点或需要我注意的事情时，能通过私聊的方式主动告诉我？」

拆开就是三个约束：**要主动**（不等用户问）、**要会中**（不是会后总结）、**要能私聊推**（不是写进纪要）。

单靠任一层都不成立：

- 纯 LLM 轮询：每几分钟烧一次 token，长会成本线性增长，且延迟高
- 纯规则：抓不到语义（"我方口径不一致""客户真实关注的是增量导入"这类）
- 纯会后：满足不了"会中就要知道"

三层各自跑明白的结论：**规则层负责"立刻知道"，模型层负责"看得更深"，会后层负责"完整归档"。**

## 三、防刷屏六件套（缺一条就会被嫌吵）

1. `once` vs `repeat`：宽泛上下文信号整场只报一次；高价值信号可重复
2. 同规则冷却 ≥5 分钟（默认 8 分钟）
3. 文本级去重（`rule:文本前 60 字`）
4. 单场硬上限 10~12 条
5. 每轮最多推 1 条
6. **首启从日志末尾跟（EOF）**，绝不 `offset=0` 回灌历史

外加误伤抑制：`once` 类要求句长 ≥8 字；中文要防子串误命中（`(?<!测)试用`、不要用裸 `包`、不要用 `对吧？`）。

## 四、验收方法（照着做）

1. 拿一场**已知内容**的会议日志，`--replay --no-send` 全量回放
2. 人工过一遍命中列表，逐条判「该报 / 误报 / 漏报」→ 改词表
3. 重复到误报 ≈0，再开实时推送
4. 实时模式跑起来后核对：`state.offset` 是否从文件末尾起算、首轮是否 0 条推送、静默期是否不推
5. 留审计文件（每条推送含原文行），会后可并入纪要「会中已提醒你的 N 项」

本次回放实测（疆海 Jira 选型会，前 26 分钟）：7 条命中，全部有效——竞品基准(17:03)、评分/偏离表风险(17:03)、审判式发问(17:09)、我方承诺(17:13)、我方失手(17:13)、**AI 被当面否掉(17:22)**。L2 补到规则层抓不到的：李阳说"任务只能一行一行填"被佳永纠正可 Excel 导入（口径不一致）、Pascal 追问"全量的导入吧"（真实关注是日常增量导入而非开荒迁移）。

## 五、成本口径

- L1：0 token（纯正则，脚本内完成）
- L2：每 5~6 分钟一次，只喂**增量**字幕（≈1.5K in / 0.3K out），一场 1 小时会 ≈¥0.01
- L3：不变

## 六、调参建议

| 诉求 | 参数 |
|---|---|
| 更安静（纯知识分享/内部会） | `--cooldown 900 --max-alerts 5`，只看 🔴 |
| 更勤（关键选型/谈判会） | `--llm-every 180 --cooldown 300` |
| 只要零成本 | `RADAR_LLM_EVERY=0` / `--no-llm` |
| 事后补救漏报 | `--replay`（state/audit 落 `.replay` 后缀，不污染实时状态） |
