# 超长字幕 → 结构化纪要

## When to Use（触发）

- 旁听完一场长时间会议 / 直播（会议纪要类 skill 负责格式，本 skill 负责**采集与压缩**）
- 用户丢来一份长逐字稿、长字幕文件，要求总结
- 单场转写在 300 句以上，或会中聊天事件上万条
- 用户看完一份拆解/纪要类产出说「没看懂」「到底发生了什么事」→ 直接跳到「第三步 输出结构」，按事件块重讲

核心目标 **用最少的 token 换到完整的事实**。原样把长转写读进上下文是最贵的做法，先做零成本的机械过滤再读。

## 第一步 采集（静默旁听两种模式）

| 模式 | 命令 | 前提 |
|------|------|------|
| 直读（推荐） | 用户本人在会 → 字幕轮询走 `--as user`，**不入会** | 用户在场 |
| Bot 挂机 | `lark-cli vc +meeting-join --meeting-number <9位> --as bot` | 用户要求「你以 bot 身份进去但别说话」 |

- **flag 陷阱**：`vc +meeting-join` 只认 `--meeting-number`（9 位会议号），传 `--meeting-id` 报 `unknown flag`。而 `vc +meeting-list-active` 返回的是长 meeting_id，两者不能混用。
- **「进去但不要说话」的正确做法**：join 成功后**不要启动语音管线**（main.py / 豆包 TTS）。没有管线就没有 TTS，天然静音，比依赖 wake-word 门控更保险。
- 启动后自检一句：`ps aux | grep -E "main\.py|meeting_chat_reply" | grep -v grep` 无输出 = 不会出声音也不会发弹幕。
- 长会/长直播结束时 poll 脚本会自动退出并给出 notify；**收到 notify 立刻处理**，别拖。
- **启动自检（别只看进程起来就报「已开始旁听」）**：起完 `sleep 20~30s` → `wc -l ~/meeting_logs/<id>.jsonl` + `tail -2` 看两句真实字幕。进程存活 ≠ 有字幕（部分会议不推 transcript 事件、或智能体开关关闭导致脚本预检即退）。真拿不到就如实告诉用户，别让它静默空跑一小时
- **多场并行（实测一天 5 场、其中 2 场同时在跑）**：一场一个 poll.sh 进程 + 一个按 meeting_id 命名的日志，自己在回复里维护一张小表（`会议号 / 标题 / 日志路径 / 是否在跑`），用户随时能校对
- **notify 交错是常态**：正在给 A 场写卡片时 B 场结束 → 先记住 B 的 notify，把 A 的成套卡片发完再处理 B，**绝不因为新的一场就跳过上一场的纪要**（用户自有 skill 里有历史事故记录）。交付顺序按会议结束时间
- **用户说「静默旁听」但没点名会议** → `lark-cli vc +meeting-list-active --as user` 把**所有**在会中的会议逐场开一路。若只返回 1 场而用户说「两场」，第二场多半是临时会议/个人通话（该接口只返回已预约的标准会议）→ 直接要 9 位会议号，别反复重试接口
- **每场产出各自成套卡片**，不要几场合并成一张；卡片 `note` 里写清会议名 + 时间区间，否则用户回头分不清哪张是哪场

## 第二步 预压缩（零 token，必做）

用 `scripts/prefilter_transcript.py`，它做四件事并把统计打到 stdout：

1. **字幕去重**：按 `sentence_id` 去重（同一句会多次推送修正版）
2. **丢填充行**：字符数 < 16 或去掉语气词/笑声后不足 3 字的行整行丢弃。实测 785 句 → 546 行 / 24.7K 字符，省掉约三分之一，正文信息不丢
3. **聊天去噪**：会中聊天事件量极大（实测单场 23 万条事件），去重后往往只剩 20 条唯一消息，绝大多数是 `THUMBSUP` / `VC_SoundsClear` 这类系统噪音。只保留长度 > 3 且非系统表情的消息
4. **链接归属**：`re.findall(r"https?://[^\s，,）)]+", text)`。主持人在贴嘉宾介绍时通常紧跟分享者的分享文档/体验入口链接，用「链接前后最近的一条长消息」把 URL 归属到具体人

另外先看一眼 **说话人句数排行**（脚本会打印）。主持人往往占最多句数，真正的内容在每位分享者 60-110 句里，按这个顺序分段提炼效率最高。

### 旁听日志（`~/meeting_logs/<id>.jsonl`）走 `scripts/transcript_paragraphs.py`

自己旁听回来的会不用先想压缩策略，一条命令出「体检报告 + 分段正文」：

```bash
python3 scripts/transcript_paragraphs.py ~/meeting_logs/<meeting_id>.jsonl
# stdout: 事件类型计数 / 时间范围 / 说话人句数排行 / 会议室麦占比 / 段落数
# 产出:  <id>.paragraphs.txt，每行一段 [说话人] 正文
```

- **先读体检报告再决定读多少**：说话人排行一眼看出这场是「单人独白」（一人占 300+ 句 → 全读）还是「多人对话」（要按人分段），会议室麦占比一眼看出归因质量
- 同一说话人的连续句子合并成段，短会也能压：实测 1154 句 → 172 段 → 去语气词后 133 段；346 句 → 213 段 → 167 段
- 合并时**保留说话人名字**，不要把 Room 麦折叠掉（折叠掉就没法判断谁是客户、谁是自己人）
- 输出后仍要 `wrap_for_reading.py` 折行再读（长段落会被 `read_file` 行内截断）

### 读的时候

- 不要整份塞进上下文。分段读，边读边把每位分享者的要点写进工作文件，再组装
- 长转写里嘉宾可能只显示用户 ID（如 `user343849`），结合上下文或聊天记录里的嘉宾介绍对应出真名
- 主持人念的观众提问 + 嘉宾回答是**含金量最高的一段**，别只提要讲的部分

### 读回来：先折行，再 `read_file`（否则静默丢内容）

压缩后剩下的长段仍可能有 2000+ 字符。直接 `read_file` 会在**行内**截断（输出里出现 `[truncated]` 字样），你会在毫不知情的情况下漏掉整段发言的后半部分。实测一场 2.5h 会议把 40,742 字符压进了 106 行，其中 6 行被行内截断，只能重读。

正确做法：先把每段折成 ≤100 字符/行的临时文件，再用 `read_file` 配 `offset`/`limit` 分段读（40K 字符 ≈ 680 行，3 次读完，零丢失）。

```bash
python3 scripts/wrap_for_reading.py <meeting_log.jsonl> /tmp/tr_wrap.txt
```

- 🚨 **中文折行必须 `break_long_words=True`**：中文没有空格，`textwrap.wrap(text, 100, break_long_words=False)` 会把整段当成一个「长单词」而完全不折，输出行仍是几千字符 → 照样被截断，白费一轮。默认值就是 `True`，别改
- 每段输出头写成 `### [序号] 说话人 @HH:MM:SS (len=N)`，读的时候能直接对照时长定位，回头引用也有稳定编号
- 折行件是**一次性产物**，放 `/tmp/`，不要写回 `meeting_logs/`

## 第三步 输出结构（用户明确要求过，别搞反顺序）

**第一块必须是「发生了什么」**，用完整故事讲清事件本身：谁、原来靠什么吃饭、后来发生了什么变化、他因此丢了什么。骨架、概念、分人要点都排在它后面。

这条来自真实反馈。一次文章拆解卡片直接上了降秩骨架和抽象概念，用户看完说「我看完还是没看懂，到底他发生什么事了？」——抽象骨架在作者脑子里成立，在读者脑子里没有落脚点。

其余结构：

- 概览用 `column_set` 放 3-4 个数字（时长 / 参会人 / 字幕句数 / 关键计数）
- 每位分享者一块，或按「作品速览 → 踩坑经验 → 可复用方法」分卡
- 多张卡片结尾标注「卡片 N/M」
- 最后一块必须落回「对**你**有什么用」，把内容拉回用户的实际工作
- **必须有一块「⚠️ 这次没做到的 / 归因说明」**——凡是本次实际存在的缺口都逐条写明：C360 被拦导致没有客户情报、会议室麦导致部分发言无法归因到个人、用户提前离会导致后半段缺失、外部文档搜索只返回链接拿不到标题所以没能筛材料。用户接受「没做到 + 原因 + 补救选项」，**不接受把推断或会议片语包装成事实**。这一块和正文同等重要，不是免责声明
- **每场保留一份可读逐字稿副本**：`cp /tmp/<id>.txt ~/meeting_logs/<meeting_id>.transcript.txt`（JSONL 里全是噪音，回头要复查时读这份），并在卡片里把路径给用户
- 底部 `note` 写清来源、时间、是否 AI 整理

### 路演 / 比赛 / 多人短分享类（每人 8 分钟）的变体

这类会的正文天然是**并列**的，别硬串成一条叙事线：

- 概览数字：队伍总数 / 从多少支初赛晋级 / 会议时长 / **字幕实际覆盖了几支**（缺哪支要如实写出来，不要拿「10支队伍」糊过去）
- 每支队伍一块，字段固定：负责人 + 部门 · 用了什么工具栈 · **量化数字原样照录**（省多少万 / 省多少工时 / 提升百分之几 / 覆盖多少型号）。量化数字是这类会唯一的硬通货，一个都不能被概括掉
- 高层/评委的追问**单独成一块**：他们的追问就是下一单的需求清单——点名要跟飞书研讨的能力、被要求「快速纳入开发日程」的颗粒度，比作品本身更值钱
- 收尾给「**可复用到其他客户的打法**」3 条并写明理由 —— 用户看完长内容几乎一定会追加「按我的身份筛」，别等他问第二次

卡片语法与分片规则见 `feishu-card-send`。

### 培训 / 内部宣讲类（单主讲 + 答疑）的变体

这类会的价值**不在「产品是什么」，而在决策规则与对客口径**——用户听完是要拿它去筛客户、跟客户说的：

- 概览 `column_set`：时长 / 手写字幕句数 / **内部北极星指标**（例：「两周内让 Tag 拿到铁饭碗」）
- 分卡：① 概览 + 一句话结论（含官方类比对象，例「对标 Claude Tag」）② **判断尺**：什么场景适合 / 什么绝对不适合（正反并列，越具体越好）③ 目标画像 + 申请流程 + 收费与时间口径 ④ **答疑精华**（逐条一句话）+ 用户自己的待办
- **把口径和红线原样抄下来**：「尚未正式发布 / 只支持定向邀请 / 属期货，不承诺开通时间」「内部材料不外发、日程不转发」——这些最容易在摘要里被蒸发，却是事后最需要的
- **写清发言分工**：主讲（产品）、答疑补充（产研）、主持（流程与材料分发）——同一问题不同人答，权威级别不同
- **答疑是这类会的第二正文**，别只提要讲的部分；点出「哪个字段决定成败」（例：报名表里「想落地的场景」写得含糊会被直接拒）
- 收尾必须给「**客户会怎么问 → 怎么答**」的现成话术 + 用户自己的 2-4 条动作项（含反常识提醒，例：个人自建没意义、得推 leader 建）

### 客户调研访谈类（为后续工作坊 / 方案做前置调研）的变体

这类会的产出**不是产品能力清单，而是客户真实痛点 + 客户对 demo 的即时反馈**——写出来要能让用户直接拿去设计工作坊或方案：

- 概览 `column_set`：时长 / 字幕句数 / **客户方到场人数**（这是最关键的结构信息，见下）/ 会议性质（调研访谈 ≠ 产品演示）
- **先写客户划的边界**：客户开场常自划范围（例：「我只负责物流交付，公司机密数据不方便讲」「供应链 function leader 是联创，采购/制造/品质各有负责人」）→ 直接把它翻译成**这次没挖到的部分**（例：只拿到物流视角，制造/采购/品质的负责人没来），并提醒用户「用这个视角设计工作坊会被同一批人指出缺口」
- **客户原话痛点单独成块，保留他的比喻与金句**（例：「食材有限、灶台很多，怎么还能把饭煮好、还快」）。比喻是客户自己的认知锚点，比转述准确得多，也最容易被他认可
- **客户对 demo 的反馈是全场最值钱的一段**：既抄肯定（「真的已经很不错了」）也抄他点出的缺口（例：「你缺了很重要的一个部分——生产制造环节」）。缺口即下一步改造清单，要点名它对应的系统/部门（例：MES、质量控制）
- **单独一块写「客户已经在用什么」**：客户自述「我们现在已经在用 X 做这个事情，只是自动化程度低」这类信号，价值高于任何需求表述——说明需求已自我确认，卡点往往只剩一个（安全评估、预算、IT 决策链）
- **推进路径必须写清责任人与阻力**：谁对谁（客户先向 A 反馈 → 平台方直接找 A）、唯一阻力（例：信息安全要走 IT 评估）、客户自己的偏好（例：要真实场景共创，不要模拟数据）；缺口的补救动作（再约采购/制造/品质一轮）
- **收尾落回用户身份**：机会窗口 + 顺序提醒（例：别让工作坊跑在安全评估前面，否则做完照样卡住）

### 内部复盘 / 周会类（一人主持 + 多人轮流汇报）的变体

这类会信息量最大但主线是「大盘 → 每个人 → 可复用打法」，别按时间顺序流水账：

- **卡 1 大盘**：负责人的复盘——净增/完成率/NDR/人效等硬指标 + 横向排名（跟其他区域/团队比）+ **做得好的与做得差的各自点名** + 两个「倒数第一」这类必须死磕的项 + 新下的 KPI + 纪律提醒（新政策/没做过的 case 先抛群讨论、对客前 re 方案）
- **卡 2 用户自己的那一段必须单独成卡**，不要折进大盘里。内容：他的指标、他讲的方法论/对客洞察、他贡献的案例与数字、他提出的风险信号、别人（尤其负责人）当场给他的分工与要求。**这张卡是用户唯一会反复回看的一张**——他关心的是「我讲了什么、我拿了什么、我被派了什么」
- **卡 3 同事的打法**：按「谁 + 一句话打法 + 可直接抄的动作」提炼，这是这类会对他最实在的产出（例：先用 X 锚定再谈怎么送、续约救单的四人配置、先让客户用起来而不是先验证需求）
- 概览 `column_set` 用团队级硬数字（不是会议时长），并在 note 里写清哪张卡是他自己的
- 会里提到的竞品/外部动态（例：某客户与外部 AI 厂商共创 N 个场景）**要单独摘出来当成风险信号**，这类信息往往比业绩数字更影响他下季度怎么打

### 用户要求复盘「他自己那一场分享」（highlight / lowlight）的变体

触发：「你听了我整场的分享吧，我这场的 **highlight 和 lowlight** 是什么」——要的是**诚实评估，不是表扬**。结构固定：`✨ Highlight` → `⚠️ Lowlight` → `一句话总结 + 一个最高优先改进项`（只给一个，并列十条等于没给）。

- **先定位「他自己那一段」**：去重 + 按时间排序后打**说话人句数排行 + 每人时间区间**（实测本人 156 句 / 09:02–09:18 = 全场 33%）→ 立刻知道精读哪段、他在全场占多重
- 🚨 **必须连读紧随其后的他人点评与弹幕**：亮点/暗点常不在他自己嘴里，而在别人对那一段的反应里。实测他把总监弹幕里的 3 条**提问**读成「谢谢你的总结」，总监当场纠正「不是给你的总结，是提问」——这个尬点才是全场最真实的 lowlight，只读 transcript 完全看不出来。`chat` 事件要单独按时间轴读一遍
- **Highlight 按「可被抄走的资产」写**：战法可复制、把「AI 难用」翻译成「AI 该这么用」的具体动作、姿态得当（主动声明边界）、选题踩中会议主轴。每条都要能落到「别的同事拿去就能用」
- **Lowlight 按四层拆，每层后跟一句「下次怎么改」**：① 结构（最值钱的方法论被压在超时后的末尾，本可当开场钩子）② 数据缺口（只给自己的测算、没给横向锚点）③ 闭环缺失（只讲打法、没讲战果/金额/复购）④ 边界只声明了一半
- 语气铁律：**该扣分就扣分**，不堆形容词、不写「讲得很好」——用户要的是下次怎么改

完整模板与实测案例（含启动旁听进程的就绪自检）见 `references/meeting-review-and-listener-launch.md`。

## 第四步 主动挖信号（会中预警 + 会后归因）

用户 2026-10-14 明确问过：「有什么办法能让你**主动**去挖掘会议中的冲突、异常项，或者某个人背后的需求？」——这类需求的标准交付**不是方案描述，而是可运行的脚本 + 开关 + 验收记录**（先跑起来再优化）。这条也在做「用户问 → 立刻落地成能力」的示范：回答里要给脚本路径、启动方式、参数、以及一份「我用今天这场会回放验证过」的证据。

规则集与推送实现见 `feishu-meeting-listen/scripts/meeting_radar.py`（该 skill 用户自有，随 poll.sh 自动启动）；本 skill 负责**可迁移的部分：怎么在长字幕里找出值得打断用户的信号**。

三层，按成本从低到高，先跑得起来再上模型：

| 层 | 做法 | 延迟 | 成本 |
|---|---|---|---|
| L1 规则层 | 正则词表扫**增量**字幕，9 类：审判式发问 / 我方主线被否（"今天不谈 AI"）/ 竞品与选型 / 商机 / 决策链 / 风险(PII·迁移·陪标·评分不公) / 我方失手 / 我方当场承诺 / 情绪场压 | 秒级 | **0 token** |
| L2 模型层 | 每 5~6 分钟把**新增字幕**（不是全文）喂轻量模型，强制 JSON：`{level,type,who,evidence,why,action}`，只推「高」，其余合并成一条汇总 | 分钟级 | ≈¥0.01/场 |
| L3 会后 | 回到本 skill 第二步（预压缩）+ 第五步之后的输出结构出纪要 | 会后 | 同现状 |

规则层可直接跑 `scripts/transcript_signal_scan.py`（**只读、零 token、任何 JSONL / 纯文本都能跑**）：

```bash
python3 scripts/transcript_signal_scan.py ~/meeting_logs/<id>.jsonl          # 回放扫描 + 体检报告 + 按规则分组命中
python3 scripts/transcript_signal_scan.py <id>.jsonl --per-rule 8 --top 40   # 看更多候选，用于调词表
python3 scripts/transcript_signal_scan.py /tmp/xxx.txt --json                # 纯文本也吃；--json 便于二次筛选
```

> 脚本自带**去重 + 按时间排序**（JSONL 行序 ≠ 时间序）和**会议室设备麦占比**提示；它只出候选清单、不做推送抑制，是给人过目用的。
> 三层设计的完整记录、规则分类表、验收方法、成本口径与调参表见 `references/proactive-signal-mining.md`。

**上线实时推送前必须先回放数误报**。实测三处误伤：`试用` 命中「测**试用**例」、`包` 命中「**包**括」、`对吧？` 命中任何人。新写的规则表第一件事就是拿一场已知会议 `--replay` 跑一遍，人工过命中列表，再谈推送。

**实时推送的刷屏控制（缺一条用户就会嫌吵）**：宽泛信号（竞品/商机/决策链）标 `once`（整场只报一次）；高价值信号可重复但同规则冷却 ≥5 分钟；同一句去重；单场硬上限 10~12 条；每轮最多推 1 条；**首次启动从日志末尾（EOF）开始跟**，否则会把会前半场一次性回灌成十几条预警。**宁可漏一条，也不要刷屏** —— 用户对「吵」的容忍度远低于「漏」。

### 别人问「刚才那场为什么吵起来了 / 他为什么这么大意见」

这是长字幕分析里最常被追问的一类，输出结构固定（2026-10-14 疆海 Jira 选型会，用户明确表示这种分析「挺有意思」）：

1. **第一行给判断**：是/不是对方在呛，以及到底呛的是什么（功能对错 ≠ 打法与立场）
2. **对方提了什么问题** —— 归类成表（逐项对标 / 具体功能逼问 / 立场性要求），每条附「我方答的什么」与「答在哪个档位」（真不支持 / 需配置 / 需集成+插件）
3. **根因分层，从浅到深**：被封口的卖点 → 审判式提问节奏 → 他觉得评分不公允 → **他的真实算盘（投入产出、陪标判断、席位规模）** → 个人处境（赶场、出差、本以为是「答疑」）。**最后一层常常才是火气的真正来源**，别停在「客户态度差」
4. **会中 vs 私下分开写**：会上多数并没有失态，只是私下吐槽——不要把私聊里的火气写成会议现场冲突
5. **收尾给 1~2 条可直接执行的动作**（如按对方的评分表做书面逐项应答、把「人工配置」从扣分项改写成「实施工作量」）
6. **归因不确定的显式标注**（会议室麦、ASR 听歪的品牌名）

## Pitfalls

- **长跑脚本的「结束检测」必须区分三类信号，且跨进程计数不能写在子进程里** → 会议结束后脚本不退出 = 没有 notify = 下游（纪要、跟进）永远不触发，实测空转 324 轮才被发现。真实根因：Bot 模式下会议结束后 API 返回 `{"ok":false,"code":120004,"msg":"bot is not in the meeting"}`——既不是「明确结束」也不是「明确否定」，被当成「探测失败，继续轮询」。修法：① 每类结束信号单独分支：`meeting has ended` / `"status":"ended"` / **`"leave_reason":2`（散会时对所有人推一次，最权威最快，`--as user` 与 `--as bot` 都可见）** / 连续 2 轮「bot 不在会」② 兜底计数器必须回到父 shell：`$((...))` 写在传给 `python3 -c "..."` 的字符串里会被**父 shell 提前展开**成数字字面量，子进程内的自增永不回写父进程 → 让 Python 只打印 `NEW`/`EMPTY` 标记，计数与判定都在父 shell 做。教训：**凡是「探测失败」和「明确否定」共用一条分支的结束检测，迟早被限流/超时坑成僵尸进程**
- **想省 token 就直接 `read_file` 整份长转写** → 上千句全进上下文，后面每一步都在为它付费。先过脚本
- **嘉宾自述的「坑」被当成闲聊丢掉** → 那是长会里唯一不可替代的部分。主持人明确要求嘉宾讲踩坑的场次，优先提炼这一段
- **把案例引用当成会议对象** → 字幕里被提到的公司/产品不一定就是本场主题，标题写了谁才算谁
- **只读字幕不读聊天** → 分享文档、体验入口、资料包链接基本都在聊天流里，字幕里没有
- **会议结束后才想起来处理** → 字幕文件是增量的，脚本每轮写盘，但纪要和跟进日程要趁热做
- **用户中途就某个名词提问，直接拿字面去搜** → ASR 会把英文名/品牌名听歪（实测会上「克劳 Tag」→ 实为 Anthropic 的 Claude Tag）。正确顺序：先 grep 实时 JSONL 拿上下文原话（`grep -n -i "tag\|claude" ~/meeting_logs/<id>.jsonl`，或按说话人过滤）还原真名，**再**去外部核实。字面直搜往往一无所获，还会把答案带偏。外部核实怎么打（厂商官网优先、从页面内嵌 JSON 取官方发布日、搜索引擎被挡时的兜底、以及「第一行先给是非判断」的回答结构）见 `references/verify-product-facts-from-vendor.md`
- **以为旁听日志是新文件、发现一堆旧字幕就慌** → poll.sh 首轮用 `--page-all` 会**一次性回填整场历史**（实测开场 6 分钟就写入 790 行）。判断增量看最后几行的时间戳，不要按总行数、也不要按文件 mtime 判断「是否串了会」
- **直接从 JSONL 统计「多少人入会 / 谁到场」** → **旧日志**里 `join` / `leave` 每轮都重复追加（实测同一场 2.5h 会议 transcript 1,278 条，而 join 65,869 条、leave 37,038 条、chat 2,849 条）→ 这种日志的进出事件只能当噪音，绝不可用来做人数统计或「谁在场」的结论。**2026-10-12 起 poll.sh 已补事件级去重**（chat 按 说话人+内容+message_id，join/leave 按 说话人+时间；已用冒烟测试验证两轮相同事件只落 3 行）。判断手上这份日志属于哪种：新日志单场 join 约等于真实参会人数（实测 5~20 条），仍是几千上万条就是旧日志，先自己按 `(type, speaker, time)` dedupe 再统计。聊天同理，先按 `(speaker, text)` 去重——2000+ 条里绝大多数是 `OK` / `THUMBSUP` 这类系统噪音
- **旁听进程为什么停了 / 为什么空转** → 先读脚本最后一行输出，三种收尾各有含义：`=== 会议已结束（API 直接返回 meeting has ended）` = 正常结束；`=== 用户已离会且 Bot 未入会，退出（静默旁听模式）` = 你已不在该会（2026-10-12 起的行为——旧版会在这时切 `--as bot` 后无限空转，日志里能看到几千轮无新事件）；`=== 智能体入会开关已关闭，无法监听` = 会议 owner 没开开关，脚本预检即退、一条字幕都不会有。看到最后这种要立刻告诉用户换办法，不要等。第四种：`=== 会议已结束（API 返回 status=ended，第 N 次轮询）` = 2026-10-13 新补的正常结束信号——此前 poll.sh 只认 `meeting has ended` 字样，而会议真的结束后 API 返回的是 `{"status": "ended"}`，识别不到 → Bot 模式下留下僵尸轮询，直到被别的会话或人工 kill。**收到一个「正常退出」的 notify 时先别急着写纪要**：兄弟会话可能已经顺手清掉你的进程并把产出交付了，先按「同一客户/事项的跟进日程」那条去重流程查一遍，再决定是否出卡片
- **会议在实体会议室里开 → 字幕说话人被记成会议室设备名** → 实测「Shenzhen-Jinghu Plaza(深圳景湖大厦)-F15-03🎦[应急会议室](13)」，一场 1,154 句里 **537 句挂在它名下（47%）**。两个后果：① 说话人句数排行失真（排第一的「人」是一间会议室）② 大量内容无法归因到个人。做法：统一改写成 `(会议室麦)` → **按内容线索推断归属，并在产出里显式说明不确定性**（例：「537 句归属到会议室麦，我按内容推断到个人，个别可能有偏差」），绝不要把推断当事实写进纪要；同时点出「有几个人到场但没发言/换地方开」这类结构性事实。`scripts/transcript_paragraphs.py` 会自动检出设备名并打印占比
- **把开场宣传片的音频当成发言** → 会议正式开始前场地常循环播放品牌宣传片，ASR 会把它记到某位参会人头上，产出多段高度近似的品牌文案（实测 1,393 / 730 / 191 字符反复出现，占掉开场 20 分钟）。过滤规则：**字数 > 200 且前 150 字出现在另一长段里 = 回声/重复，丢弃**
- **写多行长 Python 用 `python3 -c "..."` 内联** → 引号地狱之外，还可能被网关守卫误判拦下（报「cannot restart or stop the gateway from inside the gateway process」这类与命令本身无关的理由）。一律 `write_file` 写成 `/tmp/xxx.py` 再 `python3 /tmp/xxx.py`：好调、好改、好复用，也不受 shell 引号与守卫影响。两个已踩过的具体坑：① 脚本里带中文时优先用 `python3.11`（本机 `/usr/bin/python3` 对无编码声明的中文文件会报 `Non-UTF-8 code ... no encoding declared`，加 `# -*- coding: utf-8 -*-` 也可）② f-string 里塞 `\"ok\": true` 这类带反斜杠的片段会直接 `SyntaxError: f-string expression part cannot include a backslash`，把判断串先赋给普通变量
- **同一客户/事项的跟进日程变了就 `+update`，别新建第二条** → 一天连开多场会很容易攒出一堆撞车日程（实测一天 5 场会建了 8 条）。做法：建前先 `lark-cli calendar +search-event --as user --query <关键词> --start <当天> --end <次日>` 去重；事情进展了就 `lark-cli calendar +update --as user --event-id <id> --summary ... --description ...` 改写那条（例：上午建「约人事专场」，下午平台方自己开了第二场 → 把那条改写成「测试账号 + 材料补齐」，而不是再建一条快造日程）。建完保留 `event_id`，并在汇报里逐条列出建了什么（0 条也要写「本场无个人待办，未建日程」）
- **🚨 同一场会可能被两个会话同时处理 → 交付前查「已产出物」**：会议邀请会**并发投递到所有活跃会话**（旧会话没过期 + 新会话各收到一份）。实测两个会话都入了会、都读了同一份 JSONL，A 已发纪要卡片 + 建好跟进日程并 kill 掉轮询进程，B 收到「正常退出」通知后若不复核就会再发一遍卡片、再建一条撞车日程。**出卡片 / 建日程前必查**：① `lark-cli calendar +search-event`（同主题「跟进：…」）② `lark-cli im +chat-messages-list --chat-id <home> --as bot --order desc`（返回字段是 `data.messages`，不是 `data.items`，取错会误判成「没发过」）③ `session_search(query=<客户名/事项关键词>, sort="newest")`。命中任意一处 → 只给一句状态汇报 + 「已出过纪要卡片和跟进日程，不重复发」，**既不要沉默，也不要重跑全流程**。详见 `duplicate-delivery-guard`
- **用户中途离会 / 切到另一场会 → 本场后半段永久缺失，要主动补救而不是假装完整** → 实测用户在分享进行到一半（19:18）切去了另一个会议，脚本按「用户已离会且 Bot 未入会」正常退出，日志只覆盖 19:04–19:18（前 14 分钟）。做法：① 立刻为新会议开一路旁听，并在回复里说明「已自动跟到新会」② 卡片里**明确写出缺失区间**、哪几段只听了个开头、哪段完全没听到（例：刘鑫主持的「搭建」分享一段都没拿到）③ 补救优先走妙记：`lark-cli vc +search --query "<系列名>" --as user` 可检索同系列往期会议的智能纪要（实测某系列 EP18 / EP19 均能搜到）→ 用它补回没听完的场次；**当期的妙记通常会后生成，只能提「稍后大概率会出，要的话我去拉」，不要承诺马上有**
- **C360 拉不到客户情报时，用本地历史会议日志兜底，并在产出里标明来源** → 首选现成脚本 `python3 ~/.hermes/skills/productivity/c360-cli/scripts/mine_meeting_logs.py <客户简称>`（同 speaker 合并成段 + 去重 + 截断，输出可控）；线索不明时再 `grep -ril "<客户名>" ~/meeting_logs`。能还原客户的购买形态、在用产品、参与角色、历史诉求与投诉。产出里逐条标明「来自历史会议记录，不是 CRM 数据」。**绝不因为 CRM 取不到就把「客户情报」留空、更不编造**；宁可写「本次没拿到 CRM 情报」并给出原因与重试选项。C360 侧诊断与兜底的完整流程见 `c360-cli` 第 15 条
- **JSONL 行序 ≠ 时间序，读字幕前必须先排序** → poll.sh 每轮 `--page-all` 把新事件追加到文件末尾，**同一轮内的句子顺序是随机的**。实测一场 3 分 40 秒、57 句的短会，按行序读出来是前后颠倒的对话（结论句出现在背景句之前），极易把「结论」写反。**短会最危险**——句数少会让人以为「扫一眼就懂了」。有旁听日志时优先用 `scripts/transcript_paragraphs.py`（自带排序）；手写解析必须去重 + 按 `time` 排序：

```bash
python3 -c "
import json
seen=set(); rows=[]
for l in open('$HOME/meeting_logs/<id>.jsonl'):
    d=json.loads(l)
    if d.get('type')=='transcript' and d['sentence_id'] not in seen:
        seen.add(d['sentence_id']); rows.append((d['time'], d['speaker'], d['text']))
rows.sort()
for t,s,x in rows: print(t[11:19], s, ':', x)
"
```

- **起长跑旁听脚本时别用 `nohup` / `disown` / `setsid`** → Hermes 的 terminal 会直接拒绝 shell 级后台包装（提示改用 background 参数），白白浪费一轮。正确写法：`terminal(command='bash .../poll.sh <长meeting_id> "<标题>" bot', background=True, notify_on_complete=True)`（第三个参数 `bot` = 一开始就用 `--as bot` 轮询，用户不在会的场次用）。**起来后必须另起一次调用做就绪自检**：`sleep 25` → `wc -l ~/meeting_logs/<id>.jsonl` + `tail -2` 看两句真实字幕 → `ps aux | grep -E "poll.sh <id>|meeting_radar"` 确认两个进程都在；**进程存活 ≠ 有字幕**，没字幕就如实说，别让用户以为在采集

## 相关 skill

`feishu-meeting-listen` / `meeting-minutes` / `meeting-audit` 是用户自有，负责旁听链路与纪要格式规范；本 skill 只补**长内容的压缩技术与输出叙事顺序**。收到 notify 后的完整动作序列（纪要 → 建跟进日程 → 会后待办分发）以那两个 skill 为准。
