# 飞书产品销售话术 / 竞品分析

## 铁律：先验证，再论断

**所有论点必须可追溯到一个可验证的数据源。** 用户会逐一拆穿经不起推敲的论点——一次被拆穿，后续所有论点的可信度归零。

数据源优先级：
1. **用户提供的内部文档**（one-pager、产品功能表、销售培训材料）——最可靠
2. **官方帮助中心 / 产品页面**——可公开验证
3. **真实的客户会议记录**（旁听字幕、妙记转写）——客户视角，最说服力

**禁止**使用以下来源构建论点：
- 推测"这个产品应该能/不能做 X"
- 行业常识"一般来说这种产品..."
- 竞品公开资料的片面解读

## 标准工作流

### 0. 加载产品能力参考和内部文档索引
**每次执行前，先读取以下两个文件：**
- `references/feishu-ai-capabilities.md` —— 豆包/Aily家族/WorkBuddy已验证能力矩阵
- `references/internal-doc-index.md` —— 已搜到的内部关键文档及其token（额度分布、推广实践、计费说明等），避免重复搜索

### 1. 接收任务 → 先问素材
```
用户要求做 Deep Grill / 竞品分析 / 销售手册
→ 不急着开始分析
→ 先问：有没有内部产品能力对照表 / one-pager？
```

### 2. 验证能力矩阵
- 逐条列出待对比产品的**已知能力**（仅限已验证的）
- 标注每个能力的数据源
- 对未验证的能力显式标注"待确认"

### 3. 找真实差异点
- 不编造差异——不是"功能 X 比 Y 强"，而是"场景 A 只能 X 做到"
- **如果两个产品都能做某件事，就说都能做。不要为了差异化而编造差异。**
- 有效的差异通常来自：生态位置（原生 vs 外部）、用户路径（谁在操作）、数据流（数据在哪处理）

### 4. 构建话术
- 话术必须能从已验证的能力推导出来
- **处理不了的场景要诚实说"做不到"，比硬推更有信用**
- 区分"有效论点"和"会被拆穿的论点"——自觉标注后者

### 5. 输出格式
- 用户要求飞书文档时，先确认格式和存放位置，再执行
- 默认使用表格 + 场景分类的结构

## 销售作战手册文档结构

当用户要求写一份面向客户的销售策略/作战手册文档时，使用以下结构——核心诉求是**能落地**，不是喊口号。触发词：销售手册、作战地图、playbook、售卖策略。

### 文档框架

```
🎯 目标（量化指标 + 时间窗口，如"20个AI企业版客户 + 500万ARR"）
💭 思考题（2-3个核心难题，每个附可执行回答，不是问答对而是作战方案）
📊 产品/场景/商业化矩阵（画板 or 表格）
📈 消耗加速策略（来自内部文档验证过的数据）
💰 销售转化链路（分步骤，有4周落地时间表）
📎 附录：参考来源
```

### 关键原则

1. **目标是骨架，思考题是血肉。** 先定目标，再用思考题倒逼可执行方案。
2. **每个"策略"必须有落地时间表 + 验收标准。** 没有时间表的策略 = 无意义的空白文档。
3. **全员推广路径必须拆到可操作的阶段。** 如"全员开通Aily" → 拆成六阶段：高管先行→项目组建→培训开通→场景驱动→保温运营→深度锁定。每个阶段有角色、动作、验收标准。
4. **来源必须是飞书内部文档。** 用 `lark-cli docs +search` 搜，`lark-cli docs +fetch` 拉全文，链接放入附录。优先查阅 `references/internal-doc-index.md`。
5. **消耗加速三板斧**：扩覆盖（豆包/会议纪要入口）→ 提深度（Aily按人头配额度）→ 建场景（工作流/妙搭锁客）。

### 内部文档搜索优先级

做销售作战文档时，按此顺序搜内部资料：
1. 产品能力 & 计费 → `飞书AI版本对比` + `最新AI功能介绍`
2. 额度消耗逻辑 → `AI额度分布逻辑与配置建议`
3. 推广落地实践 → `AI时代企业引入飞书-上线与运营推广实践`
4. 商业化数据 → QBR数据分享

## Aily 分享侧重点（客户验证）

基于和生客户反馈，Aily 演示/分享不要罗列功能，要按两条故事线讲：

### 故事线 1：搭知识库
> "我是怎么把一个部门的知识变成 AI 能懂的"

- 入口在哪里、怎么上传、怎么组织
- 不是一次性搭完，是持续养——知识库越用越聪明
- **客户反馈：这个场景本身就很有吸引力**

### 故事线 2：搭完知识库后干活
> "知识库搭好之后，AI 能帮我做什么"

- 挂到团队智能体 → 群聊里 @ 就能问
- 智能体小队：队长分配任务，专家各司其职
- **客户反馈：这是第二个强场景，衔接自然**

### 演示顺序

```
搭知识库（种地）→ 挂智能体（养牛）→ 小队干活（收割）
```

不要一上来就讲智能体小队——客户还没看到"知识从哪来"就会问"那它怎么知道这些的"。

## 典型产品对比锚点

当对比豆包/Aily/WorkBuddy 等 AI 产品时，这些差异点通常成立（但仍需验证）：

| 维度 | 豆包企业版 | Aily | WorkBuddy |
|------|-----------|------|-----------|
| **生态位置** | 飞书内原生 | 飞书内原生 | 外部，通过 CLI/API 接入 |
| **数据流** | 不离开飞书 | 不离开飞书 | 出飞书进腾讯云 |
| **目标用户** | 全员（零门槛） | IT/业务架构师 | 研发 + 泛办公 |
| **触发方式** | 人主动问 | 事件驱动 + 定时 | 人给指令 + 定时 |
| **桌面操作** | 不支持 | 不支持 | 核心能力 |
| **飞书外系统** | 不支持 | 有限（API） | 200+ MCP |

**注意**：此对照表为通用参考模板。每次分析前必须用最新数据验证每一条。

## 已踩过的坑

### ❌ 不要做的
- 说"X 需要一个个配 MCP 连接器" → 用户反手证明 CLI 可以直接调 API
- 说"X 没有多 Agent 协作" → 用户反手给出文档证明有 SubAgent
- 说"X 没有定时任务" → 用户截图证明有
- 说"X 需要持续维护" → 用户指出 CLI 自动更新
- 说"X 体验不如 Y" → 用户指出 Bot 桥接可以同在飞书内
- 浏览器搜飞书公开页面 → 大部分时间 404 或找不到，直接走 CLI 搜内部文档

### ✅ 应该做的
- 不确定时直接说"我需要验证"
- 论点被拆穿时直接承认，不硬撑
- 所有功能对比从已验证的能力矩阵出发
- **先用 `lark-cli docs +search` 找内部文档，再用 `lark-cli docs +fetch` 拉全文** — 不要用浏览器，不要猜功能

### lark-cli 命令常见坑

- `docs +fetch` 用 `--doc`，不是 `--token`
- `docs +search` 用 `--page-size`，不是 `--limit`
- `docs +update --content @file.md` 要求相对路径。绝对值（如 `/tmp/foo.md`）会报错。改用 `cat /tmp/foo.md | lark-cli docs +update ... --content -` 通过 stdin 传入
- `docs +update --command overwrite` 会清空文档重新写入；画板块需要重新创建（旧的 whiteboard token 会失效）

## 内部文档搜索技巧

### lark-cli docs +search 的正确用法

**字段名是 `results`，不是 `items`！** 这是最常见的 bug —— 搜到了但提取代码写错字段名导致误报 0 结果。

```bash
# 正确提取
lark-cli docs +search --query "豆包" --as user --page-size 10 | \
  python3 -c "
import json,sys
d=json.load(sys.stdin)
for r in d.get('data',{}).get('results',[]):  # ← results, 不是 items
    meta=r.get('result_meta',{})
    print(meta.get('title_highlighted','?'))
    print(meta.get('url','?'))
    print(r.get('summary_highlighted','')[:120])
"
```

响应结构关键字段：
- `data.results[]` — 搜索结果列表
- `result_meta.url` — 文档链接
- `result_meta.token` — doc token，可直接用于 `docs +fetch`
- `result_meta.title_highlighted` — 高亮标题
- `summary_highlighted` — 高亮摘要
- `result_meta.entity_type` — "DOC" 或 "WIKI"

### lark-cli docs +fetch 读取文档

```bash
lark-cli docs +fetch --doc <token_or_url> --as user | \
  python3 -c "
import json,sys,re,html
d=json.load(sys.stdin)
content=d.get('data',{}).get('document',{}).get('content','')
text=html.unescape(re.sub(r'<[^>]+>',' ',content))
print(text[:5000])
"
```

### 调试搜索的步骤
1. 先用通用词（"飞书"、"AI"）测试搜索是否工作 → 确认返回总量
2. 如果返回 0，检查提取代码的字段名（`results` vs `items`）
3. 如果返回有数据但特定关键词搜不到，换同义词或拆词重试
4. 搜到文档后先读标题和摘要判断相关性，再 fetch 全文
