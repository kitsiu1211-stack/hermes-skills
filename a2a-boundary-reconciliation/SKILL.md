# A2A 能力边界对账

群里多个 Agent 互相确认「你能做什么、不能做什么」时的标准打法。对手是哨兵 / 数字员工（豆包 Mark、ISV 助手、样板间小管家）这类会反复重发同一份问题、并对「回执是否出现」下判定的角色。

## When to Use（触发）

- 对方发来「请逐条判定对错」「我俩当面对一下能力边界」「这版口径你确认吗」
- 对方发来哨兵告警：「判定：失败 / 按时 / 未见回执」「按补跑关单」
- 对方口径与你本地事实冲突，或对方重开一个明显谈过的题

## 铁律一：先查锁定版本，再回

哨兵会把同一份问题反复重发（同一个人 10-28 锁过、11-06 确认过、11-09 又发一遍 4 条判定）。**先确认这题是否已经锁过**，不要重新逐条辩论：

```bash
grep -n "口径\|逐条判定\|能力边界\|锁死" ~/.hermes/logs/gateway.log | tail -20 | cut -c1-300
```

命中历史确认 → 回复形态固定为：
1. 一句「这版和 X 锁定的口径一致，我不重开」；
2. **只列仍然错的那几项**（实战例：对方写「自动入会」和「一切记 bot 名下」，两处都要打掉）；
3. 补对方明确问的新问题。

不要把手已互认的四条再抄一遍。重复确认 = 制造下一次重开的素材，也烧 token。

## 铁律二：能力边界和凭证状态分开说

对方报「任务失败」时不要顺着它的归因走。实战：哨兵报「AI 赢单雷达 W46 失败」，真实原因是本机 `lark-c360` 会话过期，跟入会能力毫无关系。回复必须分层：

- **能力层面**：能做/不能做 + 前置条件（如「入会要 owner 开『允许智能体入会』，否则 120002」）
- **凭证层面**：谁过期、过期时间、需要谁点什么

混在一起说，会被记成「他没有这个能力」，写进对方的台账。

## 铁律三：真 @ 只能自己发，Hermes 最终响应发不出 @

Hermes Feishu 出站把整段内容塞进**单个 `md` 元素**（`plugins/platforms/feishu/adapter.py` → `_build_outbound_payload` → `_build_markdown_post_rows`，无 `at` 元素解析），所以最终响应里写 `<at user_id="ou_xxx">` 只会是字面文本，`mentions` 为空。

→ 需要真 @ 就用 lark-cli 自己发，然后把最终响应压成一段短文（只留可操作项），避免同一段内容在群里发两遍。

命令、message_id 定位、mentions 校验：见 `references/feishu-reply-with-mentions.md`。

## 铁律四：同一故障在两台机上可以有两个真因，别互相覆盖

实战（2026-11-09 C360 W46）：对方云端那台报 `session expired for online`（它 6 天 168 条日志里 `100001` 出现 0 次），我本地这台报 `code=100001`。两边身份不同——对方是 Aily（在官方管控白名单里，所以只卡授权），我这台是 Hermes（不在白名单，授权有效也照样被拦）。**两条都真，谁都不用认输**：

- 各自先跑**活体探针**再开口：先 `lark-c360 auth status --json` 看 `logged_in/expired`，再真发一条只读命令看错误码。不拿昨天的结论当今天的证据，也不拿对方的日志当自己的证据。
- 回复写成「两条并列成立 + 各自适用条件」（哪台机、哪个 Agent、哪个到期时间），不写「你说错了」。
- 对方下「这条绕不过去」的判词时，先验它是不是真物理约束。「数据只在我那台机」十次有九次就是一个 JSON 文件——问路径/体积/schema，能发就直接发，别把交接谈成长期题。发出后同时交代两个坑：字段可能含空值、隔了几个月的旧基线首跑会撞存量差（首跑只落基线不发卡）。
- 半结论要明说：「我这台没被拦」≠「授权完一定能取到数」。宣布周期通过前必须有一次成功只读的实证。

## 回复结构（实测好用）

1. 开头 `<at 本人> <at 对方>`（两个都要，群里每句话都要有人可归）
2. 「两条一起回」→ 分节：**能力边界**（逐条，只写差异）/ **任务失败**（归因 + 需要对方做什么）
3. 可操作链接单独一行（授权链接这类会过期的放最显眼处）
4. 结尾给明确承诺：「补跑完发 ✅（补跑）XXX 给你关单；本周不补我也会在这里明说」——不留悬空

## 常见坑

| 坑 | 表现 | 处理 |
|----|------|------|
| 顺着对方重开 | 又把已互认的条目抄一遍 | 先 grep 历史锁定版本 |
| 顺着对方归因 | 认了「你没有这个能力」 | 拆能力层/凭证层，显式纠正归因 |
| 拿对方日志当自己的证据 | 「你那台没报 100001」被当成我这台也没拦 | 各跑各的活体探针，只报本机实测错误码 |
| 接受「数据只在你那台机」 | 交接卡成长期题、没人动手 | 先问文件路径/体积/字段，能发就发 |
| 不知道对方 bot 的 open_id | @ 不上人，话没人接 | `lark-cli im +chat-members-list --chat-id <oc_id> --page-all --format json` → `bots[]`/`users[]` 里的 `member_id`；输出首行是 `[page 1] fetching...`，先剥掉再 `json.loads` |
| 把 `<at>` 写在最终响应里 | 消息里是纯文本 `@名字`，mentions 为空 | 走 lark-cli 手动发，发完 `mget` 核 `mentions` 非空 |
| 长正文 + 最终响应重复 | 群里同段内容两条 | 手动发长文，最终响应只留 2-4 行 |
| 用 `+threads-messages-list` 找当天消息 | 只返回旧消息，total 对不上 | 从 gateway.log 取 om_ id，见 references |
