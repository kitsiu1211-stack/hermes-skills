# 新模型 / 新工具尽职调查

## When to Use

触发语：**"你研究一下 X 模型"**、"X 是什么"、"这个工具值得用吗"，其中 X 是刚发布或正在刷屏的模型/产品/项目名（用户可能只给一个名字，甚至拼写不清）。

判断标准：**没有可直接读的代码仓库，主要靠官方宣称 + 社区实测来判断** → 用本 skill。若对方给的是开源 repo，先加载 `tech-project-evaluation`（用户自有）。

目标不是写调研报告，而是让用户**五分钟内知道这东西是什么、能不能用、值不值得跟**，并且对外引用时不会被打脸。产出硬要求：**把"厂商口径"和"实测边界"分开**，最后给一句可执行的边界判断，而不是"很强/很火"。

## 与其他 skill 的关系

- `tech-project-evaluation`（用户自有，curator 改不了）：偏 **GitHub 开源仓库**评估（stars/README/代码量）。遇到开源 repo 时加载它，本 skill 补充"托管/闭源新品"的路径。
- `chinese-search-workaround`（用户自有）：中文搜索反爬绕行（头条搜索）。本 skill 的 `references/china-web-retrieval.md` 是通道矩阵，两者互补。
- `no-fabrication`：所有数字必须有来源；厂商数字要标"官方口径、未复测"。

## 步骤

### 1. 定位一手来源（顺序不要跳）

1. **官方发布博客 / 产品站** —— 闭源托管模型在 GitHub 上只有第三方工具，一手信息全在官方 blog。发布文里常有 "Nuance" 段落（自陈哪些数字是峰值口径、评测参考是谁），**这段比数字本身更值得引用**。
2. **官方文档 / API 文档** —— 拿输出形态、硬边界（上下文窗口、选项上限）、错误语义。
3. **网关模型卡** —— OpenRouter / Cloudflare Workers AI / Vercel AI Gateway 上的模型 ID 与真实单价，是"能不能马上试"的答案。
4. **HN Algolia** —— 社区质疑、竞品对比、复刻 repo：
   ```bash
   curl -sL "https://hn.algolia.com/api/v1/search?query=<名>&tags=story&hitsPerPage=20"
   # 抓某条讨论的全部评论（比网页版干净）：
   curl -sL "https://hn.algolia.com/api/v1/items/<story_id>"   # 递归 children[].text
   ```
5. **中文二手深度文** —— 官方是英文时，中文社区常补上"翻车案例"和国内适配。检索通道见 `references/china-web-retrieval.md`。

### 2. 必抓的五组事实

| 组 | 内容 | 为什么 |
|---|---|---|
| 身份 | 谁做的、什么背景、什么时候发的 | 创始人履历决定可信度（如 RLHF 作者反思自己发明的路线） |
| 命名来源 | 名字取自哪里 | 往往是最好的**人话切入点**（Jev = 杰文斯悖论；System One = 卡尼曼快思考） |
| 输出形态与硬边界 | 输出什么、不输出什么、上下文/上限 | 决定它能不能用在你的事上 |
| 定价与延迟 | 单价、token 计费方式、响应区间 | **必须标"厂商口径、未复测"** |
| 接入渠道 | 官方 key / 网关 / 开源复刻 | 决定"下一步能不能动手试" |
| 真实用量与迭代速度 | 包管理器周下载量、发版时间线、fork/issue 比 | **star 可以刷，下载量和发版节奏刷不动** |

**用量核验（30 秒，必做，别只信 star）**：

```bash
curl -s "https://api.npmjs.org/downloads/point/last-week/<包名>"   # npm 周下载
curl -s "https://registry.npmjs.org/<包名>"                       # versions 数 + time 首版/末版
gh api "repos/<owner>/<repo>/releases?per_page=10"                # tag + published_at 迭代节奏
```
Python 包对应 `https://pypistats.org/api/packages/<pkg>/recent`。
判断口径：**周下载量和 star 量级差两个数量级以上 → 大概率是刷榜或只有围观没有使用**；两周内连发四个版本 → 项目还在剧烈变动，别急着写进客户方案。

### 3. 必找的"打脸证据"（决定结论的其实是这部分）

- **长程 / 开放任务实测**：厂商 demo 都是精心挑选的封闭场景，去找有人拿它做开放任务的公开复盘
- **复刻成本**：别人多久用多小的模型复刻出 80 分版本 → 直接回答"有没有护城河"
- **社区反向工程 / 复刻 repo / HN 高赞质疑**：`GitHub API search?q=<名>` 看有没有 jevlike/kev 这类逆向项目
- **目标语言表现**：中文/非英语任务的表现（中文泛化差 → 对国内客户场景要打折）
- **话术重定义**：厂商的绝对化口号往往偷偷缩小了定义范围（"零幻觉" = 格式不出类型错误 ≠ 判断不会错）
- **行为越权**：会不会有自己的默认规则、压过用户指令

### 4. 结论写法（硬要求）

- 给**可执行的边界判断**，不是"很强/很火"：例如"有限解空间 + 高实时 + 结构化输出，超出就翻车"
- 至少一条**实测翻车案例**，即使结论是"值得关注"
- 明确**它不能做什么**，并对国内/中文场景单独标注需验证项

## 输出给本用户的写法

用户是非技术背景的飞书 AI 销售 / 落地教练，要的是能用的人话版：

- **先一句话定性 + 一个具体类比**，再上数字和结构（"会写作文的全能实习生" vs "只会盖章但极快的审批员"）
- **数字带口径**：厂商宣称的速度/价格写明"官方口径、未复测"，并给一句"别对客户吹这个数"
- **按身份筛**：不要全量摘要。给 3 条以内"对你有什么用"，每条给理由，指出对国内企业客户要额外验证什么
- **必带批评面**：实测边界 + 护城河质疑
- **来源可追溯**：结尾列 2–4 个关键链接（官方博客原文 / 独立实测报告 / 中文深度文）
- **结尾给 1–2 个可选的下一步动作**（如"拿 key 用你的真实数据跑对照实测"），不逐点确认、不反复反问
- 用户若追加"按我的身份筛"，说明上一版给太全 —— 下一版直接砍到 2–3 条并给理由

## 坑

- **只搜英文**：官方英文 + 中文二手两条腿走路；中文深度文经常独家提供翻车案例和中文表现
- **把刷屏当结论**：热度 ≠ 价值。先问"复刻要多久""它在开放任务上翻车没有"
- **引用营销数字不加限定**：首页的倍数是"特定工作流 + 峰值"，官方自己都承认处于收益较高端
- **写成长报告**：用户要的是能不能用；研究过程留在 sources 里，不要铺满回复
- **只读 README / 只读官方**：官方自述 = 厂商口径，社区实测才是边界
- **拿中文标题当实测结论**：中文号的标题和正文经常是两回事（掘金《玩了一天 REA，我号快没了》正文其实是好评 + 教程）；而且同一篇文章不同平台标题不同。**标题只能当"传播口径"证据，事实必须落 curl 正文**，抓不到正文就明写"仅见标题"
- **只查 star 不查下载量**：38 万 star 的仓库也可能只有几千真实用户。周下载 / 发版节奏 / issue 活跃度三件一起看
- **拼写不明的名字**：先按读音/首字母猜测可能的真实名，一次搜索确认后再投入；猜不中就一次问清，别让用户重发
