# Wayfinder：客户需求分析路线规划器

## 这是什么

你面对客户时，经常遇到一种情况：客户说了个方向，但具体要什么、先问什么、哪些是坑，你也不清楚。直接出方案容易跑偏，一个个追问又怕遗漏。

Wayfinder 的做法：**不急着出方案，先画决策地图**。把"需要搞清楚的事"拆成一张决策票清单，标好哪些现在能问、哪些要等前面的事搞清楚才能问、哪些现在还说不清就先不碰。每次跟客户沟通就推进 frontier 上的几张票，跨多次会话积累。

做完所有关键决策票后，才进方案/报价阶段。

## 和 grill-with-docs 的分工

grill-with-docs 处理「你有个模糊需求，我帮你一次问清楚」。Wayfinder 处理「你连该问什么还没想全，先把问题地图画出来，再跨多次沟通逐步推进」。

grill-with-docs 可以作为 Wayfinder 里 Grilling 类型决策票的执行器。

## 五个核心概念

### 决策地图（Map）

一张多维表格或结构化文档。下面挂着一堆决策票。地图只管两件事：有哪些决策、它们现在什么状态。详细讨论内容写在每张票里，不塞进地图。

### 决策票（Decision Ticket）

一张票 = 一个「跟客户推进方案前必须搞清楚的问题」。关键判据：**现在能不能把问题描述清楚**。

- 能把问题说清楚，但还不知道答案 → 变成票
- 只能隐约感觉到有问题，但说不清具体是什么 → 留在迷雾

### 迷雾（Mist）

你隐约知道这个方向有坑（比如「数据安全」「预算审批流程」「IT 部门阻力」），但在当前阶段连具体问题是什么都描述不出来。这些不强行拆票，记在迷雾区。等前面的票解决后，迷雾通常会自己散开——散开后能描述的问题，再转成新票。

### 前线（Frontier）

当前能推进的一批票。一张票进 frontier 的条件：
- 票本身还没解决
- 没有被其他未解决票阻塞
- 当前阶段适合推进（不是那种「等客户签完合同再问」的票）

每次跟客户沟通前，看一眼 frontier，挑 2-3 张票带进去。

### 四类不确定性（四种票）

不同类型的不确定，需要不同的解法。

| 类型 | 适合解决什么问题 | 怎么做 |
|---|---|---|
| **查证（Research）** | 需要外部信息：竞品在做什么、飞书有没有这个能力、客户公司组织架构、行业惯例 | 查资料、问内部、搜案例、读文档 |
| **验证（Prototype）** | 靠讨论无法判断：客户到底会不会用、某个功能演示后反应如何 | 做 demo、给试用、拿真实反馈 |
| **追问（Grilling）** | 依赖客户/内部判断：预算范围、决策人偏好、时间预期、对方案的接受度 | 在沟通中直接问清（可调用 grill-with-docs） |
| **明确（Task）** | 已经足够清楚、可以直接执行：报价、写方案、安排演示 | 直接做，不需要再讨论 |

核心原则：**不要急着把所有票都转成「明确」。先走完查证 → 验证 → 追问的链路，等关键不确定性消除了，再进明确。**

## 流程

### 第一步：收拢已知 + 摊开未知

从客户说的内容里，提取三类信息：

1. **已明确的事实**：客户说了什么、给了什么背景、有什么约束
2. **能描述但不知道答案的问题**：拆成决策票，分四类
3. **隐约感觉到但说不清的问题**：记入迷雾区

### 第二步：画依赖关系

哪些票必须先解决，后面的才能问？标阻塞关系。比如「预算范围」（追问）没搞清楚之前，「要不要上高级版」（明确）就是悬空的。

### 第三步：建地图

用飞书多维表格建一张决策地图。**一个客户一张地图**，用「场景/项目」字段区分不同方向的需求。

#### 决策票表

| 字段 | 说明 |
|---|---|
| 场景/项目 | 这条票属于客户的哪个方向（如「客服 AI」「知识库」） |
| 决策问题 | 一句话说清楚要搞清楚什么 |
| 类型 | 查证 / 验证 / 追问 / 明确 |
| 状态 | 待解决 / 进行中 / 已解决 / 暂缓 |
| 阻塞票 | 哪些票没解决之前这张不能动（多选关联） |
| 答案/结论 | 解决后回填 |
| 备注 | 上下文、客户原话、相关链接 |

筛选「场景/项目=某个方向 + 状态=待解决 + 阻塞票为空」就是该方向的 frontier。

#### 迷雾表（单独一个表）

只记方向性描述，不设类型和状态。字段：

| 字段 | 说明 |
|---|---|
| 场景/项目 | 属于客户的哪个方向 |
| 迷雾描述 | 隐约感觉到的问题，当前还说不清（如「数据安全合规可能有坑」「IT 部门可能会有阻力」） |
| 触发条件 | 哪些票解决后这片迷雾可能会散（关联决策票表） |
| 备注 | 为什么觉得这里有坑、从哪听来的

### 第四步：推进 Frontier

每次跟客户沟通前后：
- 沟通前：打开地图，筛选「待解决 + 未被阻塞 + 当前阶段适合」的票，挑 2-3 张
- 沟通中：逐张推进，拿到答案或发现新问题
- 沟通后：更新票的状态和答案，检查迷雾有没有散开的新区域

### 第五步：关键决策完成 → 进方案

当地图里「追问」和「查证」类票全部解决，剩下的「明确」类票可以直接执行时，停止 Wayfinder 流程，进入方案/报价阶段。

## 触发方式

Agent 自主判断是否需要启用 Wayfinder。判断标准：客户需求满足以下任意两条就建地图。

- 方向模糊——客户说了目标但没说怎么做
- 多决策点——中间明显有多个需要确认的事
- 跨会话——一两次沟通搞不定
- 有迷雾——你隐约感觉某些方向有坑但说不清

满足 1 条或以下：直接推进，不建地图。客户催得急的小需求也不建。

建地图前不请示，建完后告知用户「已为客户 XX 建需求决策地图」+ 给 Base 链接。

### 会议旁听触发

旁听客户会议结束后，在产出纪要 + AI 场景提取之后，自动判断是否需要建地图。

判断依据：
- 会议中客户提了模糊需求（「想用 AI 做…」「我们也在看…」「有没有办法…」但没有具体方案）
- 涉及多个部门或决策链不清晰
- 你评估至少需要 2 次以上跟进才能理清

命中任意一条 → 建地图，从会议字幕中提取已知信息填进去，未知的拆成决策票。告知用户「会议中识别到模糊需求，已建决策地图」。

## 铁律

1. **地图优先**——模糊方向不进地图前，不跳去出方案
2. **迷雾不硬拆**——说不清的问题不强拆成票，等前面清了它自己会散
3. **前线推进，不全量轰炸**——每次沟通只带 2-3 张 frontier 票，不要一上来把十几张票甩给客户
4. **类型决定做法**——不要把「查证」当「追问」去问客户，也不要把「追问」当「明确」自己拍脑袋
5. **地图是活文档**——每次沟通后更新，下次打开一眼能看到进度
