# 会议雷达 —— 会中主动预警（2026-10-14 落地）

> 用户诉求（原话）：「有什么办法能让你**主动**去挖掘会议中的冲突、异常项，或者某个人背后的需求……发现异常点或需要我注意的事情时，能通过**私聊**主动告诉我？」
> 结论：做成 `meeting_radar.py`，随 `poll.sh` 自动启动，三层机制，**规则层零 token 且秒级**。

---

## 一、三层机制

| 层 | 实现 | 延迟 | 成本 | 职责 |
|---|---|---|---|---|
| **L1 规则层** | `meeting_radar.py` 内置 9 类正则规则 | 秒级（≤15s） | **0 token** | 冲突/审判式发问、AI 被否、竞品、商机、决策链、风险、我方失手、当场承诺、情绪场压 |
| **L2 模型层** | 每 `--llm-every`（默认 360s）把**增量字幕**喂 `deepseek-chat`，JSON 结构化输出 | 分钟级 | 一场会 ≈ ¥0.01（flash 级，输入只算增量） | 挖「人背后的需求」「我方口径不一致」这类规则抓不到的语义信号；只推 高 级，中 级合并成一条汇总 |
| **L3 会后层** | 现有 `poll.sh` → 纪要卡片 | 会后 | 同现状 | 深度纪要；**应把雷达审计文件里的预警条目并进纪要**（"会中已提醒你的 N 项"） |

## 二、启动与开关

**默认随旁听自动启动**（`poll.sh` 预检通过后 nohup 起雷达），无需额外操作：

```bash
bash poll.sh <meeting_id> "<标题>" [bot]      # 雷达同一进程组自动拉起
```

环境变量（都可选）：

| 变量 | 默认 | 说明 |
|---|---|---|
| `RADAR_ENABLE` | `1` | 设 `0` 关闭雷达 |
| `RADAR_CHAT` | Home DM `oc_e2f79ec…` | 预警私聊目标（chat_id 或 open_id） |
| `RADAR_LLM_EVERY` | `360` | L2 扫描间隔秒；`0` = 关 L2（纯规则，零 token） |

单独起（调试/补跑）：

```bash
# 实时跟（首次启动从日志末尾开始，不回灌历史）
python3 meeting_radar.py <meeting_id> --title "会议标题"

# 回放已存在的日志（测试规则、补救漏报；state/audit 落 .replay 后缀，不污染实时状态）
python3 meeting_radar.py <meeting_id> --replay --no-send --cooldown 0

# 常用调参
  --interval 15     日志轮询间隔
  --cooldown 480    同规则冷却秒数（防同类刷屏）
  --max-alerts 12   单场会推送上限
  --idle-exit 1800  日志静默多久退出
  --no-llm          只跑规则层
```

状态与审计：

```
~/.hermes/cache/meeting_radar/<mid>.state.json    # offset/已发/冷却/计数
~/.hermes/cache/meeting_radar/<mid>.alerts.jsonl  # 每条推送审计（含原文行），会后可并入纪要
~/meeting_logs/<mid>.radar.log                    # 雷达运行日志
```

## 三、防刷屏设计（重要）

1. **`once` vs `repeat`**：宽泛的上下文信号（竞品、商机、决策链）整场只报第一次；高价值信号（审判式发问、AI 被否、我方失手、承诺、情绪）可重复但受 `--cooldown` 约束。
2. **同规则冷却**（默认 480s）+ **文本级去重**（`rule:文本前60字`）+ **单场上限**（默认 12 条）。
3. **每轮最多推 1 条**，避免一轮刷多条。
4. **首次启动从日志末尾跟**（`fresh` → `offset = size`），否则会把会前半场内容一次性回灌成十几条预警。
5. 误伤抑制：`once` 规则要求句长 ≥8 字；`(?<!测)试用` 这类负向环视避免「测试用例」误命中。

## 四、推送格式

**L1 规则命中必须带上文（2026-10-14 用户反馈后加）**：只给命中那一句，用户看不懂「承诺的是什么」。例如推过
`18:08:16 陈佳永：是的，这个回头我可以发到群里面，对，是有的。` —— 用户回「这个承诺啥，应该把承诺的上下文结合一起」。

实现：`meeting_radar.py` 维护 12 行滚动字幕窗口 `recent`，命中时取 `recent[:-1]` 过滤掉短噪音行后取最近 3 行，渲染成「上文 / 👇 命中」两段；同上文一并写进 `<mid>.alerts.jsonl` 的 `ctx` 字段。零 token（纯字符串窗口），`CTX_KEEP` / `CTX_MAXLEN` 可调。

```
⚡ 会议雷达｜🟠 我方当场承诺（会后要兑现）
《飞书项目-Jira模式空间配置沟通（疆海）》
上文：
    18:08:05 陈佳永：请勿在这个路口停留。
    18:08:07 陈佳永：哦，明白，这种就是我们通过一些插件的形式去做，有一些现成的插件可以去做文档的一些版本的管理，对。
    18:08:14 深圳--木星（9楼大会议室）(20)：对，这地方我现在确认一下。
👇 命中：
18:08:16 陈佳永：是的，这个回头我可以发到群里面，对，是有的。
👉 承诺清单入待办，会后逐条兑现并回告
```

无上文的规则命中（会议刚开场）仍只推命中句。

### 命中词 + 弱词二次校验（2026-10-14 二次反馈后加）

用户反馈原话：「**这个消息很模糊**」——指的是这条：

```
⚡ 会议雷达｜🔴 商机/商务信号
《飞书项目-Jira模式空间配置沟通（疆海）》
上文：18:26:33 这个方案其实有的。/18:26:35 账号需要是一套，是吧？/18:26:38 对，他只是一套。
👇 命中：18:26:40 陈佳永：他席位对，跳动的。
👉 金额/时间点/决策链要立刻记下，会后建跟进日程
```

两个毛病：

1. **只给结论不给触发原因**——用户看不出到底哪个词报了警。→ 现在每条 L1 命中都带一行
   `　命中词：席位`（写进 audit 的 `hits` 字段），一眼可核对。
2. **弱词裸奔**——「席位」本身不是商务信号，它高频出现在账号/权限/租户/镜像这类
   **技术配置讨论**里（这场会恰好在聊 Lark 与飞书账号能不能一套）。→ 新增 `WEAK_COMBO`：
   若某句的商务信号完全由弱词（席位/立项/增购/试用/扩大规模）撑起、没有强词
   （预算/报价/价格/采购/招标/比价/合同到期/PoC/隐性成本…），则必须**同句或前两行**
   出现「伴随词」（`1000个席位`/`多少`/`怎么算`/`计费`/`浮动`/`加席位`/`要买`…）才报。
   实现见 `WEAK_COMBO` + `rule_match()`；命中句±2 行构成 `window` 做兜底判断。

验收（回放本场会）：`他席位对，跳动的。` 不再报 ✅；`我们大概要买多少个席位？` / `席位费怎么算？` /
`席位是浮动的，按人头结算` / `先试用一个月，多少钱` 仍报 ✅；真信号（17:24 客户估「工作量 + 隐性成本」）不受影响 ✅。
`clean_ctx` 的碎片阈值从 6 字提到 8 字、上下文取 4 行，避免上文本身全是「对。」这类噪音。

### 改完规则要重启雷达才生效（实时会中）

`RULES` / `WEAK_COMBO` 是进程启动时编译的，改文件不会热更。会中改规则后：

```bash
kill <旧pid>
# Hermes terminal 工具禁止 nohup/disown/setsid —— 用 Popen(start_new_session=True) 起常驻进程
/usr/bin/python3 -c 'import subprocess,os;log=open(os.path.expanduser("~/meeting_logs/<mid>.radar.log"),"a");subprocess.Popen(["/usr/bin/python3",os.path.expanduser("~/.hermes/skills/feishu/feishu-meeting-listen/scripts/meeting_radar.py"),"<mid>","--title","<标题>","--interval","15"],stdout=log,stderr=subprocess.STDOUT,start_new_session=True)'
```

**不要删 `<mid>.state.json`**：它保存 offset/sent/冷却/条数，保留才能接着跟、不重复推。

### 单场上限会吃掉后续命中（验收时注意）

`--max-alerts`（默认 12）是**整场硬上限**，命中满 12 条后连 `once` 规则也不再推。
回放验收要放开：`--replay --no-send --no-llm --cooldown 0 --max-alerts 200`；
回放状态的冷却/去重走 `<mid>.replay.state.json`，想看全量先 `rm` 掉它。

### 回放（`--replay`）会低估命中数 —— 正常现象

冷却用的是**墙钟** `time.time()`，回放时所有历史行在几百毫秒内跑完，同一规则的第二条必被 480s 冷却吃掉。
要看全量命中做验收，加 `--cooldown 0`；线上实时跑的是真实时间差，不受影响。

## 六、调优建议（按需）

- 会议类型不同 → 规则权重不同：评审/选型会开 `--cooldown 300`；客户交流/交接会可 `--cooldown 600` 更安静。
- 想要「会中每条都别漏」→ `--llm-every 180`（成本仍可忽略，但推送会更频繁）。
- 想要「只报最狠的」→ `--max-alerts 5` + `--cooldown 900`，只留 🔴。
- 纪要阶段读 `~/.hermes/cache/meeting_radar/<mid>.alerts.jsonl`，在卡片里加一段「会中已提醒你的 N 项」，避免重复。
