# 规则型告警：误报治理与可读性

> 适用对象：所有「关键词/正则命中就推消息」的告警层 —— 会议雷达 L1、商机雷达、价格监控、
> 竞品/新闻监控、webhook 过滤器。触发场景：用户回复某条预警「**这个消息很模糊**」
> 「看不懂」「这算什么商机」「这个承诺啥」。
>
> 首次沉淀：2026-10-14，会议雷达（`meeting_radar.py`，疆海 Jira 选型会）。
> ⚠️ 具体实现落在 **feishu-meeting-listen**（用户自建 skill，curator 写入被拒）——
> 该 skill 的规则/脚本改动要由前台会话直接改文件；本文件是可跨告警系统复用的设计经验。

## 一、用户对告警质量的两次反馈 = 两条设计律

| 反馈原话 | 毛病 | 修法 |
|---|---|---|
| 「这个承诺啥，应该把承诺的上下文结合一起」 | 只有命中那一句，看不出**在说什么事** | 告警带「上文」：命中句前 2–4 行，过滤掉 <8 字的 ASR 碎片（`对。`/`嗯`） |
| 「**这个消息很模糊**」 | 只给结论不给**触发原因**，用户无法判断真假 | 告警带「命中词」，一眼可核对 |

**通用律——一条好告警 = 触发词 + 上下文 + 建议动作，缺一就等着用户回你「这什么意思」。**

真实案例（2026-10-14 18:26:40，用户判定为模糊的那条）：

```
⚡ 会议雷达｜🔴 商机/商务信号
《飞书项目-Jira模式空间配置沟通（疆海）》
上文：
    18:26:33 陈佳永：这个方案其实有的。
    18:26:35 李阳：账号需要是一套，是吧？
👇 命中：
18:26:40 陈佳永：他席位对，跳动的。
👉 金额/时间点/决策链要立刻记下，会后建跟进日程
```

用户看到的是一次「只有结论、没有理由」的报警。加上 `　命中词：席位` 之后，用户自己能一眼
判断「是『席位』两个字报的警，而这句是在聊账号配置」——**告警的可读性本身就是防误报的一部分**，
因为它让用户（而不是只有规则作者）有能力否决一条告警。

## 二、弱关键词必须配「伴随词」兜底

**症状**：单靠一个词就报 🔴，而这个词在完全不同的语境里高频出现。
本案「席位」→ 高频出现在**账号 / 租户 / 权限 / 镜像 / 集成**这类技术配置讨论里（该场会恰好在聊
Lark 与飞书账号能不能一套），于是 `席位` 裸奔命中，语义为零。

**做法**（零 token，纯正则，`WEAK_COMBO` + `rule_match()`）：

- 若某句的业务信号**全部**由弱词撑起（弱词表：`席位|立项|增购|试用|扩大规模`），且**同一窗口内没有强词**
  （强词表：`预算|报价|多少钱|价格|单价|采购|招标|比价|续约|合同到期|PoC|隐性成本|人力成本|工作量|成本`），
  则必须出现「伴随词」才算命中：
  `N个席位 / N元 / N万 / 多少 / 几多 / 怎么算 / 怎么收 / 计费 / 收费 / 费用 / 浮动 / 按人头 / 人头数 /
  结算 / 扩容 / 升级 / 增购 / 续签 / 加席位 / 席位数量 / 多买 / 多购 / 要买 / 订购`。
- **窗口** = 命中句 + 前 2 行（ASR 会把一句话切碎，伴随词经常落进相邻句）。
- **反例陷阱（踩过）**：伴随词里别放「数字 + 通用量词」。`[0-9一两三…]+(个|套|人|台|名)` 会让
  `账号需要是一套` 命中「一+套」，把刚修掉的误报又放回来。量词必须绑业务名词：
  `个席位|席|元|块|万|千|人天|用户|账号数`。
- 保留 `strong` 通道：强词命中不受伴随词约束（`预算`/`采购`/`合同到期` 本身就是商务信号）。

## 三、改动必须正反用例回归（别只跑回放）

规则收紧最危险的失败模式是**收紧过头、把真信号一起灭掉**——回放里只表现为「命中变少了」，
看不出少了哪一类。所以除了回放，直接对规则表做单测：

```python
import importlib.util, re
spec = importlib.util.spec_from_file_location("mr", "meeting_radar.py")
mr = importlib.util.module_from_spec(spec); spec.loader.exec_module(mr)
rules = {r[0]: r for r in mr.RULES}                      # (id, level, desc, regex, action, mode)
opp = re.compile(rules["opportunity"][3])
print(mr.rule_match(opp, "opportunity", text, window))    # -> (bool, hits)
```

本场会保留的正反用例（回归时直接复用）：

| text（命中句） | window（±2 行） | 期望 |
|---|---|---|
| 他席位对，跳动的。 | 含「账号需要是一套，是吧？」 | **False**（原误报） |
| 我们大概要买多少个席位？ | 同句 | True |
| 席位费怎么算？ | 同句 | True |
| 席位是浮动的，按人头结算 | 同句 | True |
| 先试用一个月，多少钱 | 同句 | True |
| 他要先试用一下 | 同句 | False |
| 我们得加席位了 | 同句 | True |
| Jira 的字段配置要镜像过来 | 同句 | False |

回放的坑（墙钟冷却、整场上限、回放态残留）见 SKILL.md「长跑 watcher 改完代码后」的坑二/坑三。

## 四、误报出现时怎么回答用户（会中读，要短）

用户会在会中读这条回复，所以**别辩护、别长篇**，三层就够：

1. **认误报 + 给命中词**：说清是哪个词触发的、为什么它不构成信号（如：`席位` 裸奔命中，那句是 ASR 碎片）；
2. **还原真实语境**：回原始日志看命中句前后 10 行，用甲方/我方、议题说清在聊什么；**ASR 糊掉的部分明说「不确定」**，别替客户补话；
3. **把注意力挪到真信号**：同一话题里真正该记的东西往往已经被另一层（L2/模型层）报了 ——
   本案 5 分钟后 L2 报出「Lark 与飞书功能对齐是选型硬门槛 / 跨国账号镜像 / GDPR」，直接告诉用户
   「会后建这一条跟进就够了」。

再补一句「已重启、新代码生效（PID / 本场已推 N 条 / 上限 M）」——会中反馈是「现在改」，不是「记下来以后改」。
