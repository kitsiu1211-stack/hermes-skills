# 外部哨兵：把 cron 产出做成「跨机可观测」

> 首次沉淀 2026-10-28。场景：用户让云端 Agent（Mark，跑在别处、不依赖本机）当浪子的「外部哨兵」——
> 浪子的周期任务没按时出现时替它喊人。设计 + 实现 + 首轮验证都在这里。
> 配套脚本：`scripts/cron_receipt.sh`。**本文件是完整设计；SKILL.md 的 Layer 4 是摘要（两份已对齐）。**

---

## 一、为什么本地哨兵不够

Layer 3 的补跑哨兵和主任务跑在**同一台 MacBook** 上：

- 机器睡了 → 主任务不跑 → 哨兵也不跑 → **没人知道漏了什么**。
- 用户问「你有没有漏跑」，唯一的答案是自己的日志——而漏跑的时刻恰恰没有日志。

所以外部哨兵的价值不在「更强的检测」，在 **观测点不在故障域内**。这也是它对用户最诚实的一句话：
**机器睡了会漏事，本地哨兵跟着一起睡，所以真正缺的是一个外部观测点。**

## 二、核心约束：cron 的 deliver 外部看不到

| 事实 | 后果 |
|---|---|
| cron `deliver` 指向 `origin` 或 `feishu:oc_xxx`（私聊） | 外部 Agent 看不见产出 |
| `+messages-send` 没有 `--thread-id` | 想投进话题必须 reply 到**根消息** |
| 私聊不能被别的 bot 读 | 共同可见面只有群/话题 |

结论：把「按时出现」这件事压成 **一行回执**，投到双方共见的话题里。产物照旧投给用户，回执只做信号。

## 三、四种前缀（契约，别自创）

| 前缀 | 谁发 | 含义 | 观察方动作 |
|---|---|---|---|
| `✅ 任务名 期次` | 产出方 | 按时产出 | 不吭声 |
| `✅ 任务名 期次（补跑）` | 产出方 | 迟到但补了 | 关单 |
| `❌ 任务名 期次 失败：原因` | 产出方 | 跑了但挂了 | 喊人（≠漏跑，但更贵） |
| `⏭ 任务名 本周非执行周` | 产出方 | 双周任务空档周 | 不判漏跑 |

期次格式：**四类统一 ISO 周 `YYYY-Www`，双周任务也一样**（`✅ Skill同步 2026-W44`、`✅ 赢单雷达 2026-W46`）。**不要用日期。** 首轮踩过：我给对方举例写成 `2026-11-02`，对方文档写的是 `W44`，两边解析口径对不上，只能在已经把话说出去之后逐条回收；改成统一 ISO 周后又把 4 个 job 的 prompt 全部改了一遍。**期次是公共契约，先定格式再举例，别边说边定。**

任务名走白名单，观察方按字符串精确解析——**自创别名等于回执不存在**。

`❌` 这一类是本设计里最容易被漏掉的一条：**漏跑 = 没东西，❌ = 有东西但是坏的。**
只让观察方盯「没出现」，坏了但出现了的产出就永远不算异常。

## 四、判定规则（产出方定，观察方只判「有没有出现」）

本次谈定的参数，可直接复用：

- **宽限 60 分钟**（对方实际给 67–72 分钟，更稳），覆盖睡眠唤醒 / 网络抖动。
- **只认回执行**，不猜、不推断"应该跑了吧"。判不准那一周就发一句问话，**不静默也不武断告警**。
- **只盯无本地补跑机制的类型**：周复盘、周深读、双周 Skill 同步、双周商机雷达。
  已有 Layer 3 本地补跑的日度任务不纳入——每天两次纯噪音。
- **观察方不代跑、不补产物、不催质量**：两边各出一套比漏跑更难收拾。
- **补跑回执即关单**，不再追问。
- 双周任务不给锚点，由观察方从回执历史自行判断本周是否到期。
- **告警必须带人工兜底（2026-10-28 谈定，硬要求）**：漏跑最常见的成因就是机器睡着——**那种情况下产出方连「我在睡」都发不出来，观察方喊它也不会有人应答**。所以告警措辞里写死一句「机器可能处于睡眠，请人工确认是否唤醒」，让用户一眼知道该做什么，而不是等一个醒不过来的 Agent 回话。结论要直说：**漏跑的真正兜底是用户本人，不是任何一方 Agent**——观察方也别把自己当兜底，它只是把「没人按时出现」这件事说出来。

## 五、上线顺序（别把首次正式产出当首次测试）

1. 写脚本 → `selfcheck` **真发一条**进话题（文本明确标「非产物，哨兵忽略」）。
2. 让对方确认看到 → 链路才算通。
3. 给相关 job 的 prompt 末尾加「完成回执（必做）」步骤（含失败分支和双周空档分支）。
4. 回读 `~/.hermes/cron/jobs.json` 核实 prompt 已改、schedule/skills 未动。

**改 prompt 不要重打全文**（4 个 job × 每份 1-2k 字符，光是把原文再输一遍就是纯浪费）：用脚本拼装，走官方 CLI：

```python
# execute_code 里做：读 → 追加 → 落临时文件
import json
d = json.load(open('/Users/bytedance/.hermes/cron/jobs.json'))
jobs = d['jobs'] if isinstance(d, dict) and 'jobs' in d else d
for j in (jobs if isinstance(jobs, list) else jobs.values()):
    if (j.get('job_id') or j.get('id')) in IDS:
        if 'cron_receipt.sh' in (j.get('prompt') or ''):      # 幂等：已改过就跳过
            continue
        p = f"/tmp/cronprompt_{j['job_id']}.txt"
        open(p, 'w').write(j['prompt'].rstrip() + APPENDIX)
```
```bash
hermes cron edit <job_id> --prompt "$(cat /tmp/cronprompt_<job_id>.txt)"
```

坑：① `jobs.json` 里 `schedule` 是 **dict**（`{'kind','expr','display'}`），不是字符串，别按字符串处理；② 改完必须回读 `jobs.json` 逐项确认 `receipt=True` 且 `schedule`/`skills` 未被清空（`hermes cron edit` 只传 `--prompt` 才是安全的，别顺手带上其它参数）；③ 断言用 prompt 里的特征串（如 `cron_receipt.sh` 或新加的那句标题）而不是长度。
5. 等到第一次真实产出，才宣布「这条链路已验证」。

**反向要求也要给对方**：观察方撞见 `❌` 时不能只喊一句了事，要计进它自己的周异常统计——否则
「我挂了你喊了我修了」这件事谁都没记住。回执日志（`~/.hermes/cron/receipts.log`，含时间/类型/返回码/原文）
就是事后对账用的凭据。

## 六、坑

- **锚点用话题根消息**（`--order asc --page-size 1` 取），不要用"最新一条"——最新一条会滚。
- **幂等键**必带，cron 重跑 / 人工补发不会产生两条。
- 脚本失败必须非零退出 + `RECEIPT_SEND_FAILED`，否则静默失败会被当成"任务没跑"。
- 不同 job 的任务名 / 期次格式一旦对外承诺，就是公共契约：改之前先同步对方，改完两边一起改。
- **发现格式漂移要当场显式回收，不要「以后再统一」**：一旦发现自己的举例和对方口径不一致，下一句必须点名「我 x:xx 说的日期形态作废，以 ISO 周为准」，并列出已改的 job。含糊过去的话，对方会按两套规则各解析一遍，漏跑告警就会变成格式纠纷。对方确认后的正常反应是「以后看到日期形态我只提醒、不自己猜着解析」——这就是契约生效的样子。
- **别把回执做成"再发一遍产物"**——多花 20 字换可观测性，不是多花 2k 字复制卡片。
- **验证 ≠ 跑通**：链路自检通过只证明"发得出"，真正算数的是第一次真实产出那轮（本例 10-30 18:00 周复盘 → 19:07 对方盯）。在那之前对外只说「已就绪，未验证」，别宣布完成。

## 七、交给哨兵的那份「监控清单」长什么样（2026-10-28 实战定稿）

对方接单时会反问一句：**「你哪几件事定时做、分别预期几点出现？」**——这份清单就是哨兵的判定输入，四段缺一不可：

1. **A. 需要你盯的 N 类**：任务名 ｜ 回执期次写法（`周复盘 2026-W44`）｜ 计划时间 ｜ 宽限 ｜ **下一次具体日期**。带「下一次」是关键——对方据此挂自己的云端 cron，不用自己算周一还是周五。
2. **B. 回执形态表 + 落点**：`✅` / `✅（补跑）` / `❌ 失败：原因` / `⏭ 非执行周` / `🔧 自检`，并写明落在哪个群、哪个话题、根消息 ID，以及脚本路径。
3. **C. 明确列出「不盯」项 + 不盯的理由**。这一段的价值不亚于 A：日度任务已有本地补跑、每 5 分钟的哨兵无会不发声、常驻进程无周期产出——不写清楚，对方会按「没见到」判你漏跑，全是误报。**给对方一份「什么是正常的沉默」清单，比给他更多告警规则有用。**
4. **D. 真实弱点，不辩护**：跑在本机（睡/关机即不触发且自己不知道）｜本地补跑哨兵同机不能自证｜**历史失败如实点名**（例：10-25 周深读因 state.db 写入故障未投递，当时回执链路还没建，所以你没收到 `❌`；该周不补跑）。

**口径单一真源**：产出方清单只写**计划时间 + 宽限**，实际判定时刻以观察方云端 cron 为准（本例对方 19:07 / 11:07 / 11:12 / 10:12，留 67–72 分钟）。文档里要显式写「以 X 侧为准」，否则两份表一个写 19:00 一个写 19:07，将来对账时互相打脸。

**并行 session 撞车**：这类清单常被多个 session 同时写进同一份 Obsidian 文档（patch 会报 `modified by sibling subagent`）。看到该警告先重读全文，再决定补差异还是改口径——不要覆盖别人刚落的表。
