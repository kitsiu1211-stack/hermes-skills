# Agent 间交接协议（A2A Handoff）

## When to Use

- 用户要搭 / 改 / 复盘一个「多个 agent 互相派活」的链路（A2A 实验、群聊多 bot 协作、orchestrator + 子 agent）
- 现有链路出现「转述失真」「回执没有产物」「agent 之间互相确认刷屏」
- 要定义交接格式、回执格式、验收标准
- 有人问「A2A 到底该怎么协同」「为什么多 agent 系统不如单 agent」

反面场景：单个 agent 内部调工具，不需要协议。

## 核心判断

**问题不在 agent 聪不聪明，在接口的形状。**

模型内部是一串向量，说出口是把向量压成词。所以 A→B 传一段自然语言，等于压缩一次、解压一次，每一跳都丢东西。

链路 A → B → C → 用户，第四个人拿到的是第一个人的转述版的转述版。中间任何一跳偷懒总结一句「处理完毕」，后面全线失真。这不是工程 bug，是架构形状决定的必然损耗。

**所以协议只干一件事，把损耗从不可控变成可核对。**

## 四条原则

### 一、原始输入直达

路由只做两件事，找到该交给谁、把原样材料交过去。不做改写。

禁止转述、禁止压成「三点总结」、禁止写「见上 / 如上 / 同上」。多段任务必须完整拼接，不许截断（截断是最常见的静默故障，接收方拿到的是一份残缺任务，还以为是全部）。

### 二、固定交接格式，五行为一条消息

```
T-编号（当天日期+两位序号，如 T-1029-01）
目标：一句话说清要交付的结果，不是动作
输入：原始链接或原文，贴全
验收：什么算完成，要能被人核对
回执：完成后回 ✅ 编号 + 产出链接 + 状态
```

「目标」写结果不写动作。写「出一份竞品对比表」不是写「调研一下竞品」，前者能验收，后者永远说不清做完没有。

### 三、回执必须带产出链接

只说「已完成」但没有链接，等于没交付。

发起方要真的去打开那个链接核验，链接不在就判未完成。不复述对方的结论，不采信口头说法。这一步最容易被跳过，也最值钱。

**校验点必须是「消息回读可见」，不是「调用返回 ok」。** 这是本协议最容易假通过的地方：发送 API 返回 ok 只证明消息进了飞书的队列，不证明它落在对方能看到的位置，也不证明 @ 生效。把 CLI 日志里 `ok=1` 当验收标准，等于用「我发了」冒充「他收到了」。

硬校验三条，每条都要落到具体 message_id：

1. **存在性**——回读这个 ID，`deleted=false`
2. **落位**——`thread_id` / `thread_message_position` 说明它在哪个话题第几条，跟约定的对账位置对得上
3. **@ 生效**——`mentions[]` 里出现对方 open_id，缺了就是纯文本，对方静默收不到

对方声称发出的回执，同样按这三条独立回读，然后复述 message_id + 位置给自己人。复述比「他说发了」值钱一个量级。

命令清单见 `references/receipt-verification.md`。

### 四、只回一次，不许互相确认

一场交接最多两条消息，派活一条、回执一条。看到别人的回执不用再回，禁止「收到你的收到」。

**这条必须显式写进协议，不能靠自觉。** 实测过，一份新规则发出去两分钟内，群里就多出二十几条「收到」「已对齐」「口径锁定」，确认本身变成了要被压缩传递的新内容，跟要解决的问题同构。

## 对账：先排除双向观测盲区

判「对方没回」之前，先假设自己也瞎。实测过一例：A 的回执确实按时发在话题里，B 的判定落在主聊天流没进话题——两边各自回读自己的日志，都得出「对方违约」，各错一半，谁都没撒谎。

对账第一条不是追责，是对齐观测面：

- 先声明「我这次核的是**话题 X**」还是「主聊天流某时段共 N 条」，口径不同就别比
- 双方都贴 message_id，不贴 ID 的判定视为没做
- 判「未收到」之前至少换一次观测面再判（话题 ↔ 主聊天流 ↔ 私聊）

群里 `chat_mode=group` 时，主聊天流消息 `thread_id` 为 null，话题里的才带 `omt_`。同一条链路里两种位置会混着出现——这正是盲区来源，不是谁偷懒。工作流类任务尤其容易踩：定时任务的判定默认发在话题，人却只看主聊天流。

## 重试护栏：别把「不可见」修成「双回执」

「不可见就重发」方向是对的，但裸着上会引出两个新故障：

- **双回执**：重发必须带 `--idempotency-key`，否则同一条判定发两遍，对方按两条独立事件处理，回执率统计直接失真
- **重试死循环**：连续 3 次回读仍不可见，停止重试、降级到主聊天直接 @ 人。静默循环比重试失败更贵——没人知道你卡住了

## 交付物披露：输入降级必须先说

比回执可见性更影响人做判断的，是「结论是在残缺输入上算出来的，却没说」。硬规则：只要输入降级（取数失败、只拿到部分消息、会话被重置、时间窗不全），交付物**第一段**就写明降级了哪块、对结论什么影响。写在附录或脚注等于没写——人只看第一段就下判断。

两边都认这条之后，它比回执协议本身更能减少返工：回执坏了是沟通成本，降级不报是判断被污染。

## 反模式

| 反模式 | 后果 |
|---|---|
| agent 之间用对话链串起来 | 链越长越慢越贵越笨，最后一环在按传闻干活 |
| 传摘要不传指针 | 「上一环节总结了三点」在工程上等于谣言 |
| 回执写「已处理完毕」 | 无法核验，等于没交付 |
| 用 `ok=1` 当验收标准 | 消息可能落在对方看不见的位置，或 @ 根本是纯文本，双方各说各话 |
| 只核自己的日志就对账 | 双向观测盲区，两边都判对方违约，各错一半 |
| 用自然语言当 agent 之间的接口 | 压缩解压各一次，每跳都丢 |
| 交接历史留在私聊 | 无台账、无法回放、无法追责 |
| 每个 agent 自己保存上下文 | 人一走认知就消失，第二个项目从零开始 |

## 落地检查清单

- [ ] 有没有一份共享台账，所有 agent 读写同一份（不是各存一份再互相转述）
- [ ] 能不能从台账把一次运行完整重放出来（重放不出来，说明系统在靠聊天运转）
- [ ] 派活消息里，原始材料是链接/原文还是你的转述
- [ ] 回执里有没有产出链接，有没有人去核验
- [ ] 验收标准是「回读可见 / 链接打得开」，还是偷懒用了「调用返回成功」
- [ ] 对账时双方有没有声明观测面（话题 or 主聊天流）并互贴 message_id
- [ ] 重发有没有幂等键，有没有「N 次不可见就降级到人」的止损线
- [ ] 输入降级时，交付物第一段有没有披露降级范围和影响
- [ ] 有没有防确认往返的硬规则
- [ ] 有没有定义「多久不回算未接入」（默认 24 小时），并有绕过机制

## 上线套路（实测有效）

1. 把协议写成一份文档，落到知识库，别只发在聊天里
2. 群里/链路里一次性 @ 全员发布，要求回一行确认（一行就够，明说别展开）
3. **预期第一小时就会冒出确认往返**，当场补第四条原则并说明理由，不要事后总结
4. 记录首轮回执率。静默的人单独补一次定向提醒（编辑原消息不算新事件，对方可能收不到）
5. 24 小时后按回执率分「已接入 / 未接入」两档，未接入的下次派活直接绕过并留档

## 常见阻力与回应

**「先别搞这么正式，跑起来再说」。** 协议本身就三行字，落地成本比重建一次链路低。先加编号和链接，其余等出问题再加。

**「agent 都很聪明，不用这么死板」。** 聪明解决的是单步质量，解决不了链路形状。三个聪明 agent 串成一条散文链，结果比一个傻 agent 还差。

**「结构化太麻烦」。** 结构化只在派活侧多花二十个字，换回来的是可核验和可回放。不结构化的代价在后面每一跳都收。
