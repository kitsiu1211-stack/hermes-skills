# Agent 间交接协议（A2A Handoff）

## When to Use

- 用户要搭 / 改 / 复盘一个「多个 agent 互相派活」的链路（A2A 实验、群聊多 bot 协作、orchestrator + 子 agent）
- 现有链路出现「转述失真」「回执没有产物」「agent 之间互相确认刷屏」
- 要定义交接格式、回执格式、验收标准
- 有人问「A2A 到底该怎么协同」「为什么多 agent 系统不如单 agent」

反面场景：单个 agent 内部调工具，不需要协议。

## 核心判断

**问题不在 agent 聪不聪明，在接口的形状。**

模型内部是一串向量，说出口是把向量压成词。所以 A→B 传一段自然语言，等于压缩一次、解压一次，每一跳都丢东西。

链路 A → B → C → 用户，第四个人拿到的是第一个人的转述版的转述版。中间任何一跳偷懒总结一句「处理完毕」，后面全线失真。这不是工程 bug，是架构形状决定的必然损耗。

**所以协议只干一件事，把损耗从不可控变成可核对。**

## 四条原则

### 一、原始输入直达

路由只做两件事，找到该交给谁、把原样材料交过去。不做改写。

禁止转述、禁止压成「三点总结」、禁止写「见上 / 如上 / 同上」。多段任务必须完整拼接，不许截断（截断是最常见的静默故障，接收方拿到的是一份残缺任务，还以为是全部）。

### 二、固定交接格式，五行为一条消息

```
T-编号（当天日期+两位序号，如 T-1029-01）
目标：一句话说清要交付的结果，不是动作
输入：原始链接或原文，贴全
验收：什么算完成，要能被人核对
回执：完成后回 ✅ 编号 + 产出链接 + 状态
```

「目标」写结果不写动作。写「出一份竞品对比表」不是写「调研一下竞品」，前者能验收，后者永远说不清做完没有。

### 三、回执必须带产出链接

只说「已完成」但没有链接，等于没交付。

发起方要真的去打开那个链接核验，链接不在就判未完成。不复述对方的结论，不采信口头说法。这一步最容易被跳过，也最值钱。

### 四、只回一次，不许互相确认

一场交接最多两条消息，派活一条、回执一条。看到别人的回执不用再回，禁止「收到你的收到」。

**这条必须显式写进协议，不能靠自觉。** 实测过，一份新规则发出去两分钟内，群里就多出二十几条「收到」「已对齐」「口径锁定」，确认本身变成了要被压缩传递的新内容，跟要解决的问题同构。

## 反模式

| 反模式 | 后果 |
|---|---|
| agent 之间用对话链串起来 | 链越长越慢越贵越笨，最后一环在按传闻干活 |
| 传摘要不传指针 | 「上一环节总结了三点」在工程上等于谣言 |
| 回执写「已处理完毕」 | 无法核验，等于没交付 |
| 用自然语言当 agent 之间的接口 | 压缩解压各一次，每跳都丢 |
| 交接历史留在私聊 | 无台账、无法回放、无法追责 |
| 每个 agent 自己保存上下文 | 人一走认知就消失，第二个项目从零开始 |

## 落地检查清单

- [ ] 有没有一份共享台账，所有 agent 读写同一份（不是各存一份再互相转述）
- [ ] 能不能从台账把一次运行完整重放出来（重放不出来，说明系统在靠聊天运转）
- [ ] 派活消息里，原始材料是链接/原文还是你的转述
- [ ] 回执里有没有产出链接，有没有人去核验
- [ ] 有没有防确认往返的硬规则
- [ ] 有没有定义「多久不回算未接入」（默认 24 小时），并有绕过机制

## 上线套路（实测有效）

1. 把协议写成一份文档，落到知识库，别只发在聊天里
2. 群里/链路里一次性 @ 全员发布，要求回一行确认（一行就够，明说别展开）
3. **预期第一小时就会冒出确认往返**，当场补第四条原则并说明理由，不要事后总结
4. 记录首轮回执率。静默的人单独补一次定向提醒（编辑原消息不算新事件，对方可能收不到）
5. 24 小时后按回执率分「已接入 / 未接入」两档，未接入的下次派活直接绕过并留档

## 常见阻力与回应

**「先别搞这么正式，跑起来再说」。** 协议本身就三行字，落地成本比重建一次链路低。先加编号和链接，其余等出问题再加。

**「agent 都很聪明，不用这么死板」。** 聪明解决的是单步质量，解决不了链路形状。三个聪明 agent 串成一条散文链，结果比一个傻 agent 还差。

**「结构化太麻烦」。** 结构化只在派活侧多花二十个字，换回来的是可核验和可回放。不结构化的代价在后面每一跳都收。
